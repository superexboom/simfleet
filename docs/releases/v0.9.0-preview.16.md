修复 GPU 长时间运行后拖慢 CPU 调度的问题：GPU 超时、回退积累排除记录后，即使手里仍有大量榜单任务，也可能只使用少量 CPU 核心。

- 将有效排除记录整理成哈希集合，每个候选请求最多序列化和哈希一次；已过期的排除记录不再参与筛选。
- 每个候选的场景键和学习记录只查询一次，已暂缓的场景直接跳过。完整批次优先、探测冷却、内存预算和回退规则保持原有语义。
- 此次为客户端修复，原生 CPU DLL 与 sfg3 GPU 套件可以继续使用同一引擎版本的现有构建。

现场有 148 个展开任务和数百行待算，10 个 CPU 线程有任务，实得约 3.2 核；GPU 调度反复耗时 200–300 ms。用现场请求、148 个候选和 256 条排除记录做单次筛选对照，重复哈希路径约 177.97 ms，改为集合查询约 0.91 ms，筛选结果相同。该数据只表示排除项查询成本，不是整机吞吐倍数。

在原有 GPU 分配失败回归用例中补充 512 条排除记录下的有效/过期排除、探测与完整批次选择断言，通过；没有新增测试文件或运行全量测试。

三平台发布检查仅运行上述直接相关的回归用例，再构建各平台安装包。CPU 原生引擎和 NVIDIA 套件沿用[当前引擎构建](https://github.com/superexboom/simfleet/releases/tag/engine-6c720edfd739)与[独立 GPU 套件](https://github.com/superexboom/simfleet/releases/tag/gpu-6c720edfd739-sfg3)。

本机部署后保留 10 核预算、8 GiB CPU+GPU 总提交上限和已有 GPU 学习记录，使用相同 `6c720edfd739` 原生 DLL 与 sfg3 套件。正常接单后的四个 3 秒采样为 9.92、9.73、9.77、9.79 核；短时观察没有新增超过 200 ms 的调度调用。这是现场恢复验证，不是固定任务吞吐基准，也不代表所有 GPU 场景超时已经消除。
