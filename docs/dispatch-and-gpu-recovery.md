# 领取等待与 GPU 超限恢复

本次诊断分别确认了服务器的领取节奏、客户端自动并发缺陷，以及 GPU 可恢复超限被误当成永久停用的问题。客户端修复合并到 `0.9.0-preview.4`。

## 领取等待的实际证据

2026-10-23 本机运行引擎 `62a82930d1d3`。公开 demand 统计约 149.8 万行，其中大部分是重新评分和扫榜；`work.json` 信号新鲜并明确显示有开放任务。请求本机身份的实网结果如下，日志不记录身份或凭据：

| 事件 | 观察 |
|---|---|
| 重启后首次设备绑定 | 769 ms |
| 首次领取请求 | 响应 695 ms，`early=true`，`next_ms=27034`，没有任务 |
| 等待到期后的请求 | 响应 1,392 ms，收到 1 行，`next_ms=60000` |
| 该行完成 | 约 270 ms 后已完成，距下次可领取还剩 59,730 ms |
| 自动补开第 2 路 | 收到 200 行，响应 1,517 ms，`next_ms=60000` |
| 自动补开第 3 路 | 收到 27 行，响应 740 ms，`next_ms=60000` |

这次启动的主要等待是服务器保留的每身份 `next_at`，重启客户端不会清掉；并非该请求在网络上挂了 27 秒。上游实现对单独派发的一行也使用 `sync_floor_ms`，实网当前值为 60 秒；每包上限为 200。全站待算总数不等于本身份此刻能领取的数量。事实确认还受独立性、网络、已答任务和派发优先级限制。

对应上游源码核对至 `ee902441e7df436570b37a01802a7fcef66a1c20`：[sync.js](https://github.com/magenie33/wfsim/blob/ee902441e7df436570b37a01802a7fcef66a1c20/worker/sync.js)、[dials.js](https://github.com/magenie33/wfsim/blob/ee902441e7df436570b37a01802a7fcef66a1c20/worker/dials.js)。结论以实网返回参数为准，源码默认值不当成部署参数。

客户端原有自动并发逻辑要求每一路都还持有任务，才允许开下一路。这会漏掉“任务很快算完但处于领取冷却”的情况。本地同条件对照给出三行正常任务和 60 秒领取间隔：旧版始终只开一路，修复版在 20 秒调度检查时补开第二路；两者都没有对同一身份提前领取。`tools/check-dispatch.py` 可复现。

修复还把设备绑定移到后台、与工作信号并行，避免某一路绑定拖住全局派单；在领取冷却期间继续按既有频率更新 CDN 信号；信号 HTTP 超时缩至 5 秒。到期的提交不再被信号等待阻塞。普通状态上报不会抢在有任务时的领取错峰等待之前发送。

UI 现在区分绑定、请求、领取倒计时、服务器未分配、网络重试、信号不可用、排空和引擎切换。`dispatch.log` 在后台写入至多两个约 1 MiB 文件，记录耗时、行数、next_ms、dials 和组序号，不记录 cookie、账号、设备身份、租约或任务正文。

若要进一步消除“单行 0.27 秒算完却等 60 秒”的上游瓶颈，需要上游调整单行/小包的下一次允许领取时间，或在发优先任务时同时补足普通工作。客户端继续遵守上游间隔，只利用用户配置的并发上限进行正常调度。

## GPU status 120

截图的 `GPU run failed, status Some(120)` 对应 runtime 的私有页不足。旧版给每局 48 个 4 KiB 页，即 192 KiB。相同武器/榜单模式的不同构筑仍可能修改更多状态，先前的测试样例不能覆盖每个构筑。

旧版遇到任何非零 GPU 状态就让 worker 退出，Manager 随后一直处于 failed 状态，直到用户重启或重新开关 GPU。这正是“一次回退后 GPU 再也不参与”的原因。

现在 `120` 和输出容量不足 `2` 按整行回退。失败行不合并、不评分，从 run 0 交给 CPU；同批完整的行继续核对、评分。GPU 进程和 CUDA 上下文保持运行，继续下一批。

出现私有页不足后，后续每局预算依次提升到 384、768 KiB，最大批量相应从 16,000 次缩到 8,000、4,000 次，私有页缓冲总预算保持约 3 GiB。失败请求的内容哈希被保留在有界的 512 项队列里，避免同一请求马上再次撞墙；不会存入永久无限增长缓存。

worker 异常退出、驱动错误或批次超时会先让在手任务回 CPU，再在 15 秒和 60 秒后最多两次重建。重建保留已识别的失败请求和内存预算。引擎/架构/哈希错误、未知状态、WASM 数值不一致仍停用 GPU，不自动重复错误计算。

12 GiB 子进程硬提交限额、系统至少 8 GiB 空余才发新批次、30 秒批次超时均保留。资源不足回退显示在累计回退行数，临时故障恢复显示倒计时；不会因为单行私有页不足把整张卡永久闲置。

## 修复验证

- release 测试 42 通过、7 个原有环境测试忽略。覆盖合法部分回退、伪造回退携带评分拒绝、未知状态拒绝，以及 768 KiB 预算下批量不得超过 4,000 次。
- 从公开 Torid 爆破使榜单抽取 30 个不同构筑，保持完整战斗时长、每构筑 8 局；与正常 Fulmin 混批。第一批 16 行成功，第二批 15 行成功、1 行返回 `120`，成功行完整评分均与 CPU 一致。
- 同一个失败构筑提高到 384 KiB 后得到正确完整评分；同一 worker 随后再完成 4 条正常行、4,000 次模拟，评分全部一致，进程没有退出。
- 实际 Fleet 回放时强制终止 GPU worker：15 秒后重建，约 4 秒后再次就绪；96 行最终全部由 CPU 正确完成，没有提交 GPU 部分结果。恢复测试峰值提交约 6.57 GiB。
- 实际部署目录启动 `preview.4` 后，现场已出现一次超限回退，GPU 保持运行并完成 11 行；资源栏显示完成 11／回退 1。此时 GPU 子进程提交约 4.4 GiB，主进程约 0.24 GiB，CPU 为用户原设定的 10 核，并发正常扩至上限 3 路。
- 同一 worker 后续再次进入计算，现场看到 5 行／5,000 次批量、程序 GPU 96%，确认超限之后仍参与新任务；此时 GPU 子进程提交约 5.0 GiB。
