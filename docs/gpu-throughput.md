# GPU 吞吐优化：preview.12 / sfg2

本轮在 RTX 5080 上对 WFSim `5c64c380e5f2` 做本地优化。客户端优先使用同引擎、同架构的 `sfg2`，没有时继续使用 `sfg1`。原生 CPU DLL 继续使用同版 PGO 构建。

## 吞吐主改动的完整客户端对照

6 种 Burston Prime 构筑，单体与多目标 base 榜单混排，循环组成 240 条离线任务；每行保持原始 1000 次模拟。新旧版本都用 10 个 CPU 线程和 8192 MiB 总提交预算，策略缓存从空状态开始。任务不向服务器领取或提交。REPLAY 时间覆盖计算与 GPU 初始化、探测，启动前的引擎参考校验不在计时内。最终轮预先生成新功能的桥接编译缓存，首次生成并初始化耗时 2.294 s；这对应持续运行和重建 worker 时可复用的缓存。另有一轮冷启动耗时约 19 s，数据保留但不把它归因于内核速度。

该回放一次性装入任务，因此不能用它单独证明生产环境扩大候选预取窗口的收益。窗口改动有明确上限，线上效果应观察真实调度日志。

| 指标 | preview.11 + sfg1 | preview.12 + sfg2 |
|---|---:|---:|
| 完整正确任务 | 240 | 240 |
| 计算阶段时间 | 83.867 s | 78.061 s |
| CPU＋GPU 工作量折算 | 1016.2 分/分钟 | 1091.8 分/分钟 |
| 其中 GPU | 198.0 分/分钟 | 273.4 分/分钟 |
| GPU 完成行数 | 48 | 60 |
| 进程族提交峰值 | 6.20 GiB | 6.32 GiB |

同一批总 work 为 `1420481629600`，逐项核对分数、metric、work 的完整多重集合及 GPU 分账。整机吞吐提升 7.4%，GPU 工作量/分钟提升 38.1%。这些是固定离线任务结果，不能预测变化中的线上队列；本表 GPU 分钟值按本轮总时长计算，与界面的滚动十分钟窗口不同。

## 保留的改动

- 对齐的 WASM 读写使用整字访问；非对齐、跨字、gas 特殊地址继续走原有路径。原来的拷贝、越界、资源限制和顺序评分保留。
- CUDA 链接使用 `-maxrregcount=96`，精确除法、平方根、非 FTZ、禁用 FMA 合并等选项保留。驱动查询的寄存器从 255 降到 96，理论驻留上限提高；没有把理论 occupancy 当作实际吞吐。
- 从已领取的任务中选择最大的同类批次；扩大有界候选窗口，每轮最多准备 16 行。收尾多留 CPU 工作，避免 CPU 全部等 GPU 的最后一批。
- 私有内存增加 256/512 KiB 档位。比如 46 页的样本可使用 256 KiB 配额，在相同约 3 GiB 私有页总空间中容纳 12000 次模拟。
- worker 上报启动后的基础提交量。调度预留实际基础量加 1 GiB，最低 2 GiB；无法测量时保留原来的 3 GiB 估算。CPU、系统可用内存、显存和最终 Windows Job 上限继续共同限制批量。
- `dispatch.log` 的 `gpu_batch_finished.timing` 记录 `prepare_ms`、`gpu_ms`、`download_ms`、`merge_ms`。第一轮混合任务中内核占 97.47%，下载占 0.08%，所以没有优先做异步搬运。
- 桥接 WASM 编译产物按源哈希和 Wasmtime 版本缓存，启动和 worker 恢复时复用。缓存不兼容或损坏时重建，不跳过结果校验。

独立 Burston 4000 次模拟从 10.163 s 降到 8.286 s；新模块 12000 次模拟为 11.324 s，全部分片和评分一致。批次大小改变的结果只用于解释供料，整机收益以上表为准。

## 排除的路线与限制

128 线程 block 在原模块上比 32 线程更慢；8 线程 block 在新模块上也没有收益，最终保留 32。把全部内存访问强制展开会使 PTX 从约 82 MB 增至 156 MB，链接触发构建预算保护，已撤销，没有运行速度结论。只扩大候选窗口曾令 GPU 多做任务却拖慢总完成时间，已修正 CPU 收尾份额，相关数据保留在验证记录中。

GPU 占用 100% 只能说明长时间有 GPU 工作，不能证明所有运算单元都饱和。该设备驱动报告 FP32/FP64 吞吐比为 64；这不是对当前内核的瓶颈归因，但意味着不能套用 FP32 或 Tensor Core 标称算力估算精确双精度模拟速度。[CUDA 属性定义](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__TYPES.html)，[寄存器上限选项](https://docs.nvidia.com/cuda/nvjitlink/index.html)。

sm120 在本机实测。sm75/sm89 使用相同已验证源码和桥接层交叉编译，清单为 `device_validated: false`；1660 Ti、40 系与其他 50 系型号的实际收益仍需目标设备测量。低内存机器可先更新客户端以获得调度和内存估算改进，更新内核则需要相应 `sfg2` 包。

完整对照之后，线上验收又发现慢任务会增加整个 GPU 的恢复退避。最终客户端将已就绪 worker 的任务超时与初始化/驱动故障区分：前者暂缓对应场景、15 秒后恢复其他工作，后者保留递增退避。重复的无收益探测也逐渐延长重评间隔。

八个探测样本改用独立执行组，以减少稀疏样本的分支互相等待。Burston 同一八样本请求从 6.475 s 降至 5.107 s；Dual Toxocyst 的真实超时请求在旧执行方式下 12 秒未完成，改动后 9.428 s 完成，八个分片均与原 WASM 相同。探测上限调整为 12 秒，收益筛选仍要求 kernel 不超过 6 秒；因此该慢场景能正常返回“暂缓”，不需要重建 worker。没有把这两项探测结果叠加到前面的整批提升数字，也没有为这些分支变动重跑已通过的全量对照。

本轮扩充五个现有直接用例，并在原 worker 文件中新增一个缓存复用/损坏恢复用例，复用了现有 CUDA 内存差分检查和 Fleet 回放工具，没有追加全量测试。机器码结果见 `experiments/gpu-board/throughput-results.json`。CPU 计算核心本轮未修改。
