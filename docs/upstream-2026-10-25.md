# 2026-10-25 上游兼容与紫卡 GPU 路径

线上引擎为 `6c720edfd739`，官方 WASM 为 `4990a5afe220`，数据包为 `f8bc96ccab7e`。本地构建对应上游提交 `98b5e28e515c531cdb24d57c2b099e989a8fdca3`；通过未修改源码计算的 engine ID 与线上一致。CPU 继续使用 `sfe2` PGO + ThinLTO x86-64-v3，GPU 继续使用 `sfg3` 的 1 KiB 页和 16 位页索引。

## 上游变化和构建中断

上游将武器 MOD 池缓存起来，并让多种静态目录通过共享锁读取，减少重复准备和多核争用。紫卡搜索增加了填充前后的两种起点处理，以及单位置搜索不能继续提升时的耦合位置搜索。这些变化均随新源码编译，不在客户端重写搜索规则。

原生 Action 的实际错误是本地 `003-static-panel-metadata.patch` 中的 `Mutex` 依赖上游父模块导入；上游重构移除该导入后，三平台都出现 E0425。补丁改为显式使用 `std::sync::Mutex`。原有静态字符串引用与有界池缓存仍保留，防止面板创建时重复泄漏。

上游还修复了派单查询计划：其提交记录指出，同步派单的候选查询曾约需 28 秒，重新分析队列表统计后约为 22 毫秒。这是上游报告的修复数据，不是本客户端的本机性能测量。

## 旧引擎的接受范围

本次 `/release.json` 仍将 `dac6ecbaf97e` 等旧引擎列在 `accepted` 中，但带有 `join: true`。按当前客户端契约，宽限期为 3 天；这种旧引擎只能领取由当前引擎独立答案先行的交叉验算任务，不能承担任意新行的首次测量。列表存在不代表任务供给和收益与当前引擎相同。

原有“等待原生构建最多 48 小时”的配置仍保持。此次部署直接选用已经完成验证的新原生引擎。

## 紫卡是否能用 GPU

| 任务 | 当前执行路径 | 条件 |
| --- | --- | --- |
| 榜单行：已经确定武器、MOD、紫卡词条与数值、场景和模式 | CPU 或 GPU | GPU 引擎必须匹配，任务探测通过且完整批次有收益 |
| 紫卡增益：搜索更优构筑 | CPU 原生优化器 | `quick_fleet` 的 lead、候选评分及最终结果仍走搜索接口 |

`src/work.rs` 的 `BoardRun::gpu_input` 与 `src/gpu.rs` 的 `eligible` 没有紫卡或武器白名单。GPU 收到 `/api/board/order` 生成的完整请求；`PreparedBoard` 在 CPU 上准备战斗状态，GPU 按原始 run 索引执行战斗，随后按原顺序合并。紫卡词条、负面、roll 与等级已包含在准备结果中。

因此，“带紫卡的榜单”已支持 GPU；“紫卡增益搜索”目前没有 GPU 接口。要扩展后者，可以把每轮候选及元素顺序对应的战斗批量送入 GPU，但需要一个专门的搜索评分桥接层：保持候选顺序、配对随机流、初筛分片续算、最佳元素顺序、标准差和 gas/work 累计一致。搜索 lead 与状态推进仍由 CPU 控制。只把搜索请求转成普通榜单行会丢失这些语义。

## 验证范围

本地 PGO 训练与优化构建的完整结果一致。新 CPU DLL 与线上官方 WASM 对照，8 条带紫卡的 Braton Prime 榜单行覆盖四个场景和 base/cycle，分数、work、gas 逐位一致；紫卡搜索 canary 同样逐位一致。

sm120 在 RTX 5080 上核对了带紫卡的 Burston Prime / standard_single_target / base：128 个战斗分片、两条短样例评分，以及四条不同随机种子的完整 1,000 次榜单评分，与原生引擎一致。完整 worker 批次约 15.78 秒；这是兼容性核对，CPU 实例及编译任务同时运行，不作为性能基准。部署后已观察到 GPU 完成五条真实 Torid 单目标任务。

没有匹配硬件的 sm75/sm89 必须标明仅完成交叉编译；它们复用同一份已验证的主机桥接代码，不能将本机 sm120 的运行结果当作其设备实测。
