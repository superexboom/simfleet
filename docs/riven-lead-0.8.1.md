# 紫卡 lead 优化（0.8.1）

客户端可以本地优化 lead，不需要修改 WFSim 服务器或等待公开 API 更新。

发布构建使用 `sfe1` 修订号：例如 `872e90ffaf0d-sfe1-v3.dll`。上游引擎 ID 不变时也能与旧 DLL 共存，新客户端优先获取新修订；旧版缺少扩展时仍可回退。修订号只改变文件选择和发布身份，不改变模拟算法。

## 实现

浏览器用的 quick-fleet 协议会在每轮评分返回后重走搜索路径。客户端已经缓存解析计划，但路径上的配装 key 和比较资料仍会反复生成。其中 preference 每次都会查找赋能和进化资料，再构造用于原有比较器的列表。只看 CPU 满载会把这些重复处理也当成有效计算。

本地原生库增加两个补丁：

- `005-deferred-lead-reports.patch`：任何起点还在等评分时，保留每个起点的派发内容和进度，跳过随后必定被调用方丢弃的答案合并、候选排名和报告准备。本轮待算队列是判断依据，不能只看最后一次评分的标志。
- `006-bounded-lead-metadata.patch`：记住 lead 重走路径时使用的配装 key 和 preference。每张表上限 4,096 项，到上限后清空并重新填充；`fresh` 开始新搜索时释放旧表，线程退出时释放全部缓存。评分端不使用这份缓存。

比较仍调用原有 `preferred`，战斗循环、候选访问顺序、预筛选规则、随机流、完整评分、最终复算和 work 计量均沿用原实现。没有减少模拟次数，也没有拿近似分数提前交结果。原生库缺失或启动对照不一致时仍走已有回退路径。

## 固定请求对照

Ryzen 7 9700X，Windows，AVX2 原生库，6 条评分线程。同一份 `riven.json`，Braton Prime、3 张固定元素卡、10 次候选评分、20 次最终模拟、3 个结果。每次在新进程启动。先做三组交替对照，之后对修正暂停标志边界的最终 DLL 复测三次；表中旧库为交替对照中位数，新库为最终复测中位数：

| 阶段 | 0.8.0 原生库 | 0.8.1 原生库 |
|---|---:|---:|
| 全部搜索 | 25.684 s | 2.472 s |
| lead 累计 | 24.226 s | 1.224 s |
| 最后一次 lead 调用 | 0.522 s | 0.032 s |

此固定请求吞吐比为 **10.39×**，首次三组交替对照为 10.36×。完整答案、103 步搜索、20,880 次候选战斗、总 work `9065743294` 全部相同。每一步的 pending/progress、每个评分切片的响应也逐一计算摘要并对照一致。这个结果说明该请求受重复 lead 元数据处理限制，不代表所有紫卡或整个站点都能加速十倍。

同一个 0.8.1 客户端、16 线程、cache 调度，12 行榜单加 1 个紫卡任务，旧库总完成时间 **34.582 s**，最终新库 **14.661 s**，13 份答案一致，约 **2.36×**。这组是单轮混合回放；新版首次试验为 14.794 s。两次新版和旧版均通过实际客户端的榜单与紫卡 WASM 对照。

第一次只跳过中间报告的试验是 26.86 s → 24.43 s；更大的收益来自有界元数据缓存。

## 验证

- 通用搜索的 3 项测试通过，包括“前面起点暂停、后面起点清除最后一次评分标志”和“旧标志残留、首个起点非法”的边界。原实现会触发新增回归。
- 原生 wrapper 的 4 项测试通过；上游多 worker 与单 worker 搜索一致、分片方式不影响 work 的两项回归通过。
- 对照 6 种请求：多起点、预筛选开/关、预算截断、Torid 自定义紫卡、同 ID 改 roll、切回原武器。完整结果与每轮报文均一致。
- 在同一进程、同一 leader 和评分线程上连续切换上述请求 40 次，结果一致。最终库的私有提交在第 10/20/30/40 次为 144.79/144.95/143.04/144.35 MiB；退出线程后为 141.54 MiB。进程同时加载旧库和新库，也包括 Python；这不是生产客户端的绝对内存值，也不能代替 1–2 天的部署观察。
- `wfsim-truth` 的限定范围穷举核对完成；quick search 保持其原有启发式搜索语义，不宣称变成全局最优求解。

可复现脚本：`tools/bench-riven.py`、`experiments/check-lead-regression.py`。原始结果保存在 `.bench-lead/`，交付包包含验证记录。DLL manifest 记录原始引擎、上游提交、每个本地补丁的 SHA-256。

部署目录已更新到 0.8.1，程序和 DLL 与验收产物的 SHA-256 一致。原有配置与 3 个 kept 文件的校验值保持一致。实际部署目录的榜单冒烟检查为 6 线程、3 次中位数 0.521232 s，分数和 work 正确。验证后退出；相邻的 `simfleet-backup-20261021-before-0.8.1` 保留 0.8.0 和 `rollback-app.ps1`。

## 是否能挪到空闲核心

lead 已经运行在计算线程上，其他核心可同时做评分或榜单；完成后提交结果并退掉 leader 线程，释放搜索状态。当前原生搜索状态保存在 TLS，不能把下一轮调用随意塞到另一条线程。修改线程的 CPU 亲和性可以改变运行核心，但不会消除搜索的先后依赖，也会影响缓存局部性。

最终候选复算彼此独立，技术上可增加本地接口，交给现有 worker 池并按原次序收集。它不需要服务器改动，但仍须等所有规定的结果算完才能提交。对于这里最后一次调用约 32 ms 的样例，继续拆分的收益有限；最终 runs 很大时才更值得做。

更进一步的做法是把整条搜索改成可继续运行的状态机，保留每个起点的当前位置、已访问集合和遍历游标，避免每轮重走。它也能只在本地库实现，但需要证明多起点顺序、预算、去重、进度与 work 等价。本版本实现的是有实测收益的报告裁剪与有界元数据缓存，尚未实现状态机或最终复算拆分。
