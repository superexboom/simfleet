# GPU 实际吞吐、活跃计速与面板设置

本轮目标是改善实际完成的有效 work。任务数、运行次数、随机种子、逐项评分及服务器权重不变。界面速度口径变化不算作性能提升。

## 先看真实损耗

2026-10-24 本机日志截取约 49.3 分钟，成功 GPU 批次 198 个，完成 1049 行，平均每批 5.30 行、5.72 秒。成功整批累计约 1132 秒；成功及失败探测累计约 354 秒；失败整批约 120 秒，失败后的最低恢复等待约 150 秒。日志采用两个有界文件滚动保存，这只是该时间段的观察，不是全天统计。

GPU 忙碌百分比只说明存在 GPU 工作，不能直接表示算术单元吞吐。当前实现把完整 WASM 模拟移植到 CUDA：每个线程执行一个独立模拟，保留动态分支、精确浮点、WASM 内存语义和逐局状态。它不能直接套用矩阵运算或 Tensor Core 的理论峰值。[NVIDIA 利用率定义](https://docs.nvidia.com/deploy/nvidia-smi/index.html)，[CUDA 控制流说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/)。

取得 NVIDIA Nsight Compute 2026.3.1 并在本地解包，未修改驱动配置。查询性能计数器返回 `ERR_NVGPUCTRPERM`。因此分支发散、指令缓存、寄存器溢出、FP64 比例仍是待测因素，不能把这些候选瓶颈写成已确诊的根因。[官方分析权限说明](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)。

## 速度口径

- CPU 速度：CPU 正在处理计算工作的时间。
- GPU 速度：GPU worker 从任务准备到计算及合并结束的时间，包含探测和失败任务的时间；没有适用任务、恢复等待、暂停时不计时。
- 总速度：CPU 或 GPU 至少有一方工作时的时间，并行工作不重复累计。设备独立时钟不同，CPU 速度与 GPU 速度不能直接相加。
- 最近窗口为各自最近 10 个活跃分钟；总平均也是活跃时间平均。等待时保留已测速度并显示“计时暂停”，恢复工作后继续推进窗口。
- 每个活跃秒合并一条计数，历史窗口有界；结果的 work 只在成功完成时归属 CPU 或 GPU，不把探测折算成贡献。

离线性能报告仍按相同墙钟区间计算完成 work/分钟，包含相应初始化、探测和失败损耗。活跃速度回答“有工作时做得多快”，总墙钟吞吐回答“现实一分钟产出多少”；二者不能混用。

## 面板操作

顶栏改为两行。第一行显示版本、状态、运行时间和时钟；第二行显示引擎和 GPU 状态。移除重复的核心数量、并发数、全站在线数。

在主面板按 `D`，或 `S → 侧栏显示项目 → Enter` 打开显示菜单。`↑↓` 选择，`Space / Enter / ←→` 切换，`R` 恢复全部显示，`Esc` 返回。支持贡献、资源、全站和排行榜整组隐藏，也能分别隐藏速度、账号、显存、内存、核心预算等子项。显示改动立即写入 `simfleet.toml` 的 `hidden_sidebar`，无需重启；隐藏全部整组后任务区自动扩宽。

## 学习缓存持久化

旧实现已在学习结果变化时调用保存，不能把问题概括成“只在退出保存”。已确认的薄弱点是写入错误被忽略、没有强制刷新或备份，以及修改总内存上限会改变绑定而使全部记录失效。

新实现写入临时文件并 `sync_all` 后替换，保留 `gpu-policy.json` 和 `gpu-policy.json.bak` 两份完整快照，启动时选择最新且匹配的快照。保存失败会显示日志并重试；启动也会报告读入记录数或缓存失效。仅内存上限变化继续复用测量，批量仍受新的实际预算限制；引擎、模块、设备和驱动等身份变化仍要求重新学习。

启动探测前保存一条“尚未完成”的记录，进程意外结束后短暂避开同一场景，保留其他学习结果。成功场景持续运行时延长有效期，减少长时间部署后的重复探测。新探测的持久化标记不抬高单局内存配额，已有资源不足记录的配额下限仍保留。

这里保证正常文件系统上的完整快照与异常进程退出恢复；不承诺硬件断电、存储故障时绝对零丢失。

## 本轮内核探索

同一组 Burston＋Furis，4 行共 4000 次原始模拟，32 线程 block 的现有 sfg2 总耗时 12.722 秒。一个线程一个 block 的候选为 48.977 秒，明显退步。优化非对齐和向后重叠复制的候选为 12.625 秒，约 0.8% 差异，一次有界对照不足以证明实质收益。候选均通过完整分片与评分对比；复制候选还通过现有内存差分检查。没有继续扫参数或重复测试求好看的结果，部署继续保留原 sfg2。

完整客户端对照使用五种武器的六类任务，共 180 行、每行 1000 次模拟，12 个 CPU 线程、8192 MiB 合计预算。旧客户端为 67.024 秒、GPU 完成 35 行；允许相近耗时场景混批的候选在修正初始内存档位后为 68.600 秒、GPU 完成 28 行，没有得到收益，因此撤回混批调度。该对照总 work 均为 `1477082727900`，完整评分多重集合与 CPU 原生结果一致。

初次候选的探测持久化标记把新场景私有内存下限错误抬高到 384 KiB，结果保留在记录中，修复后只重测候选。纯 CPU 对照有一次与最终客户端编译重叠，计时排除，只重测这一项。没有重跑已通过的全套测试。

无编译干扰的纯 CPU 对照完成同一批 180 行用了 78.860 秒，约 1123.8 分/墙钟分钟。原有 CPU＋GPU 为 67.024 秒，整机吞吐约高 17.7%；GPU 部分约 210.1 分/墙钟分钟，相当于纯 CPU 吞吐的 18.7%。这仍是单轮固定队列对照，不能预测不断变化的线上队列，更不能声称已达到 CPU 一半。最终版撤回混批候选，因此没有把候选的计时冒充最终版新增收益。

要争取达到整组 CPU 一半的实际贡献吞吐，后续更值得测量的是事件循环和状态布局：减少完整 WASM 内存访问及通用动态结构的代价，对相似战斗状态分组，必要时把热点模拟改写成适合 GPU 的专用实现。必须保持逐局 RNG、gas、浮点行为和结果顺序，并逐类与官方结果核对。这是需要性能计数器和真实任务支撑的下一阶段工作，不能仅根据显卡规格承诺倍率。
