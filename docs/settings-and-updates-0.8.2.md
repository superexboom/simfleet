# 0.8.2：运行设置、原生构建等待与 CI 优化

## 运行设置

按 `S` 从计算面板进入设置，方向键选择，Enter 编辑，Enter 确认保存，Esc 取消当前编辑或返回面板。枚举项也可用左右键切换。菜单显示本机 NUMA、处理器组和末级缓存信息，可配置：

- 离开时/使用时核心数、并发上限。
- `placement`：auto、system、numa、cache；空值等同 auto。
- `numa_nodes`：逗号分隔，留空选择全部；`cpu_offset`；`core_type`。
- 优先级、内存软线、空闲判定、电池暂停和原生构建等待小时数。

确认的设置以及原有 `+/-`、`[`/`]` 调整，在主循环下一次运行时立即写入 `simfleet.toml`，不再等到退出。文件写入失败保留待保存状态并重试；界面显示失败原因。启动时会把新增默认字段写入配置。手工修改 TOML 仍应先退出客户端，避免和运行设置互相覆盖。

Windows 可以在菜单中调整进程优先级。Linux/macOS 普通进程不能保证提升已经降低的 nice/调度等级，因此菜单会提示退出后编辑 priority，再从正常优先级的终端重新启动，不会误报实时调整成功。

核心预算和等待时长等立即生效。placement、NUMA、偏移或核心类型改变后，先保存，再停止领新任务；已有任务、续租和结果提交正常继续。排空后自动更换进程，使线程绑定与 TLS 状态在正确生命周期重建。最多排空 15 分钟，未完成任务正常交还。暂停状态下延后重启；退出仍是退出。旧进程退出后新进程读取保存的配置，不需要用户手工重开。

## 等待原生构建

`native_wait_hours = 48` 是等待窗口，不是停止检查更新 48 小时。客户端继续每分钟检查网站版本、原生发布情况和旧引擎接受期限。

1. 当前有已验证的 simfleet 原生库，且服务器仍接受这个旧引擎时，继续使用它。
2. 新引擎的 simfleet 原生库可用并通过自检后，排空任务并提前切换。
3. 自首次发现当前引擎落后起，最多等设定时长。到时使用新引擎已有的后端：官方原生库或 WASM；优化库稍后发布仍会自动下载并接上。
4. 服务器的 `accepted/until` 是硬边界。临近到期、旧引擎不在接受列表或服务器明确拒绝时，提前切换，不固定假设三天或七天。
5. 设置为 0 表示立即跟随上游。没有可用旧原生库的新安装也立即使用当前引擎。

选择的引擎及等待开始时间存储在程序旁的 `engine-state.json`。重新启动、内存维护重启、上游接连发布多个版本，都不会重置同一个落后引擎的等待窗口。保存的旧 WASM 和数据包在新版本验证期间保留，避免重启后失去可用版本。账号、计算身份和结果存档不放在这个状态文件中。

2026-10-22 的网站清单给各旧引擎分别提供接受截止时间；当时上游文档中的默认宽限期为三天。客户端不把该数值当成永久协议保证。

## Windows Actions 的耗时

运行 39751450722 的已完成步骤统计：

| 阶段 | Windows | Linux | macOS |
|---|---:|---:|---:|
| 客户端编译 | 205 s | 74 s | 117 s |
| 参考 WASM 编译 | 131 s | 52 s | 89 s |
| 原生库编译 | 367 s（两种 CPU） | 142 s（两种 CPU） | 127 s（一种 CPU） |
| WASM 一致性检查 | 439 s（两种 CPU） | 205 s（两种 CPU） | 112 s（一种 CPU） |
| Job 总时长 | 1231 s | 533 s | 524 s |

差距来自编译和真实校验成本，不能只归结为下载慢。Windows 与 Linux 的同阶段差异还受 runner 硬件/系统影响，不能从单次数据确定每项根因。

改动一：`check-native --reference-cache <file>` 只在显式指定离线参考 WASM 时启用。WASM 侧 8 行完整结果与完整紫卡参考答案按请求缓存，第二种 CPU 构建复用；原生侧每种构建仍执行全部校验。缓存指纹包含完整 WASM、数据包、引擎号、校验 EXE 的 SHA-256，并检查每份答案的校验值。正常运行不会启用该缓存，也不把它跨版本上传发布。

本机固定参考测试：首次 83.6 秒，复用参考的第二种 CPU 构建 11.6 秒，两次 `CHECK-NATIVE rows=8 skipped=0 riven=same`。这是校验阶段测量，不能当作整个远端 workflow 的保证时间。

远端实测已完成：[旧运行 39751450722](https://github.com/superexboom/simfleet/actions/runs/39751450722) 的 Windows Job 为 **1231 秒（20:31）**，[新运行 39760114759](https://github.com/superexboom/simfleet/actions/runs/39760114759) 为 **903 秒（15:03）**，缩短约 **26.6%**。校验阶段由 **439 秒降至 184 秒**，缩短约 **58.1%**；日志确认基线产生 9 份参考结果、AVX2 命中 9 份，两个构建的 8 行和紫卡均一致。原生编译为 367 → 275 秒，参考 WASM 编译 131 → 110 秒，客户端编译 205 → 183 秒。这是同一上游引擎的两轮 CI，不是多次统计；不同 runner、缓存冷热和服务负载仍会影响总时间，不能承诺每次固定 15 分钟。

改动二：CI 使用固定的独立源码工作树路径，缓存参考 WASM 和两种原生目标的编译依赖。仍按源码、工具链与补丁正常重编，不直接把旧 DLL 当作新引擎。手动 `verify_existing=true` 可重建已存在引擎来验证流程，已有发布文件不会覆盖。

## 验证

单元测试覆盖菜单导航/取消、非法值、窄窗口与双宽字符、旧配置默认值、连续上游更新不重置等待、重启序列化、接受期提前到期及被篡改的参考答案失效。`tools/check-live-settings.py` 用本地协议服务和两代真实引擎验证运行中保存、保存失败重试、继续旧原生库、重启保留等待、48 小时超时、接受期失效、0 小时等待和原生库提前到达。不会向生产队列申请任务。

发行包继续保持程序和原有四份说明/许可文件，原生库在独立 engine Release 发布。
