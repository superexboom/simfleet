# 每路线程上限与提前预取

preview.17 在 **S → 每路线程上限** 增加 `slot_threads`。单位是逻辑线程：一个启用 SMT 的物理核通常提供两个逻辑线程。默认 `0` 保持共享线程池；正数限制每一路身份下所有 CPU 计算任务合计能使用的线程数。GPU 批次仍由独立后端调度。

设置确认后立即写入 `simfleet.toml`。由于 CPU 排列与原生线程局部状态需要一起更新，改变该设置会停止领取新任务、完成手中工作，然后自动重启生效。旧配置缺少该字段时按 `0` 读取。

## 32 线程机器示例

```toml
idle_cores = 32
active_cores = 32
slots = 0
max_slots = 4
slot_threads = 8
placement = "cache"
```

对两个各有 8 核 / 16 线程 CCD 的 9950 系列，这会形成四个分区，每个分区使用同一 CCD 内 4 个物理核及其 SMT，总计 8 线程。自动模式启动时直接打开四路，每路最多使用自己分区的 8 线程。不会让第一路用全部 32 线程，也不会先把所有物理核分给一批路、再把纯 SMT 线程分给另一批路。

`max_slots` 仍是用户选择的路数上限，`slots` 非零时仍是固定路数。分区数不足以覆盖当前总线程预算时，不越过单路上限借线程：例如 32 线程预算、每路 8 线程、最多三路，最多同时用 24 个 CPU 计算线程。要覆盖 32 线程，应允许至少四路。`max_slots=0` 自动上限会包含覆盖当前预算所需的分区数，最多 64 路。

每一路的标题显示正在处理任务的线程数与该路可用线程数。`simfleet cpu` 会列出分区及其 CPU 编号；这比只看 CPU 总线程数更适合核对实际拓扑。

## NUMA、缓存、奇数与大小核

- `auto` 自动选择 NUMA 或缓存域；`cache` 尽量将一个分区留在同一末级缓存，`numa` 留在同一 NUMA 节点。大缓存域优先，但不把跨 CCD 的逻辑线程当成同一物理核的 SMT。
- 一个物理核及其 SMT 作为整体安排。奇数空位优先由可用的单线程核心（例如 E 核）补齐；没有足够独立核心时，才把少量 SMT 对拆到相邻有空位的分区。每路最多一个这种尾部空位是常见的双线程 SMT 情形，不会丢弃线程来强行凑偶数。
- Intel P/E 核按系统拓扑识别。默认先把完整 P 核分配到各分区，再用 E 核补位；各分区在容量允许时混合 P/E 资源。`core_type=p/e` 仍决定优先顺序。例如 6P＋4E、共 16 线程，单路上限 5 时，三个满分区可各放两组 P 核 SMT 加一个 E 核，余下一个 E 核形成尾部分区。
- `slot_threads=1` 或最后只剩一个逻辑线程时，无法让每一路都独占完整物理核；这时显示实际线程额度，不承诺各路等性能。NUMA/缓存域边界也可能产生小于配置上限的尾部分区。
- 路数多于 CPU 分区数时，多路轮流使用同一个分区；物理线程不会复制，也不会超出总预算和每路上限。
- `placement=system` 或平台未提供可绑定 CPU 拓扑时，仍执行逻辑线程额度限制，但物理核绑定由系统管理，不能保证 SMT 配对落点。Windows/Linux 有可用拓扑时可使用 `auto/cache/numa`。

总线程预算运行中缩小时，已发出的短任务先结束，新任务按缩小后的额度分配。若正在执行的紫卡搜索所属分区改变，由于搜索状态保存在原线程中，会等当前调用结束后在新分区重新开始该搜索，避免带着旧线程状态跨核恢复。

## 预取与领取间隔

协议 8 的剩余工作估算会扣除正在计算的行已经完成的比例，并记录同步往返耗时。共享模式至少预留服务器低水位，或者一次领取间隔加两次网络往返及少量缓冲，取较大者。启用每路限额后，预取窗口还会至少覆盖服务器一包目标时长的一半，并在允许时请求一整包后续工作。按默认参数，相当于提前至约 5 分钟剩余量。

每一路独立保存服务器的领取截止时间、网络失败退避和错峰时间。preview.19 不再因其中一路收到空包而收缩其他路；自动模式重启时在 CPU、内存与用户并发上限内恢复已有身份，新身份仍按实际供给与利用率逐步增加。有过量积压或资源预算缩小时，仍会减少接单路数。

服务器的 `next_ms`、每路持包上限、每包行数和失败退避继续生效。没有工作时的任务信号和错峰等待会在领取间隔内提前准备，自动并发的利用率判断从 20 秒缩短到 5 秒。

这个设置改善客户端的任务分配和补给重叠，不能制造服务器尚未发放的工作。若所有允许的路数都处于领取间隔，或服务端不提供任务，CPU 仍可能空闲；应结合每路状态与 `dispatch.log` 判断。

## 验证

使用已有测试补充双 CCD 大缓存、NUMA/处理器组、奇数额度和 P/E 混合核心的断言；新增一个混合拓扑用例。Windows 实际绑核检查通过。配置默认值、菜单编辑与提前预取函数的相关用例通过。

既有 `tools/check-dispatch.py` 增加分组模式：在本地假服务器上用真实原生引擎运行，7 个线程、每路上限 3、三路并发，观察到 3＋3＋1 的线程分配；所有记录都在所属分区内，未超过每路上限；存在手中仍有任务时的预取，提前越过领取间隔的请求为 0。未联系生产任务服务器生成测试任务，未运行全量测试。

随后针对“路数超过分区数”的轮转分支，使用 7 线程、每路上限 3、固定六路：六路均计算并提交了结果，分区范围与线程额度核对通过，提前领取次数为 0。

9950/X3D 与 P/E 混合场景属于拓扑逻辑验证，本机实际绑核和联调使用 Ryzen 7 9700X。上述核对不是这些不同 CPU 的吞吐基准。
