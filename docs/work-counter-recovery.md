# CPU 异常工作量与计数恢复

2026-10-27 北京时间 09:04:38，preview.19 / 引擎 `14c617506965` 的一条 CPU 榜单结果报告了 `gas = 4,607,178,437,394,868,700`，对应 `work = 230,358,922,269,743,420`。换算成展示分数约为 230,358,922.27 分。原战斗评分字段是 `6.3244318701136635 kpm`；异常出现在计量字段，不能据此认定战斗评分一定正确。

该结果进入第二路待交文件后，污染了“速度”“CPU速”和“待交”的本地显示。本次已保存快照中只有这一条异常，另有 1,250 条正常待交结果。同期 GPU 完成批次的工作量是普通范围；异常行完成时间与该 GPU 批次不同，且 GPU 输出已有安全整数校验。

上游协议 8 的 `worker/sync.js::parse` 要求 `work` 为非负 `Number.isSafeInteger`。只要一条结果不合法，整份请求会返回 HTTP 400。因此不应只在 UI 限制位数或把贡献截断：这还会影响正常结果提交。本次诊断时的追踪尚未记录到这条结果触发的 HTTP 400，不能把潜在后果写成已发生事实。

## 修复范围

preview.20 在 CPU 榜单结果进入统计、待交和网络层之前，检查有限非负评分、非空指标、非负且不超过 `2^53-1` 的 work，以及可选计数器的整数范围。

无效原生结果保存到 `result-diagnostics/last-invalid-score.json`，保留上一份诊断，包含引擎号、原始请求、场景与异常输出，不带账号凭证。整行从 run 0 改用官方 WASM 重算一次，既有 native accumulator 不复用，GPU 也不再抢走这次参考重算。只有重算后的合法结果能计分和提交；参考路径仍失败则交还该行，避免无限重试。

启动时逐个检查待交日志，将不合法记录原样保存至 `result-diagnostics/<身份前缀>.json`，从提交队列中移除。提交筛选和待交求和也检查合法性，即使诊断目录无法写入，异常值仍不会随正常结果提交。正常结果、账号、设置、历史已确认贡献不修改。此次旧异常行只有结果而无完整输入，不能伪造正确 work 或冒充重算成功。
