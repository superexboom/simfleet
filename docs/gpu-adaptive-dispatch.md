# 无武器白名单的 GPU 调度

本页记录 preview.6 的策略与验证。preview.12 的批次选择、内存档位、独立探测执行组及 12 秒探测上限见 [GPU 吞吐优化](gpu-throughput.md)。

`0.9.0-preview.6` 删除 `eligible()` 中 Fulmin、Zenith、Torid 的名称判断。正常榜单请求只检查结构和有界资源：存在武器 ID、非空 ruler、有限且 0–600 秒内的时长、1–1000 次模拟。不是按名称拒绝未知武器，也不把资源上限误当作算法支持范围。

## 学习路径

1. CPU 使用原引擎生成完整请求。GPU 无已知结论时，复制该请求做本机探测；CPU 原行继续派发，不等待探测，也不修改服务器租约。
2. 探测保持原 runs/seed/duration，从原始 run 0 到末局之间均匀选最多八个索引。CPU 桥接 WASM 逐个计算参考分片，GPU 执行相同索引并逐个比较完整分片。
3. 同版原生 prepared ABI 做两次小样本测速，取较小值减轻冷初始化/调度抖动影响；GPU 记录 kernel 耗时和最大写入页数。初筛要求 kernel 不超过 6 秒、保留内存余量，并估算扩大批量后至少有约一个 CPU 核心的补充能力。这是保守启发式，不是对满批性能的精确预测；Furis cycle 的实测表明，探测 4.26 秒也可能在正常批量中有价值，因此没有用固定 3 秒门槛拒绝它。
4. 初筛通过后，该上下文可参与整行 GPU 批量。按已测页数加余量选择 192/384/768/1536 KiB；同批上下文相同，继续受合计 8 GiB 内存和约 3 GiB 私有页总缓冲约束。
5. 完整批量每行继续做第一局 WASM canary、完整顺序合并和原评分。若实测每行 GPU 时间超过估算的单核 CPU 时间 25%，暂缓该上下文；资源失败也暂缓，整行回到 CPU，其他上下文继续。

探测响应没有 score，不能经过 Fleet 的答案提交路径。原请求 runs 保持不变，探测不是把 1000 改成 8 的另一场计算。已取消/已在 CPU 完成的任务也不会因探测结果重复提交。

## 有界缓存和重试

上下文键包括 ruler 以及除构筑相关字段、seed、runs 之外的完整请求字段。敌人、等级、模式、阵型、时长以及未来新增的上下文字段都会隔离。不同构筑仍可能成本不同，因此小样本结论要接受每个完整批量的后续反馈；一次慢构筑可能让同场景暂缓，不宣称同场景所有构筑绝对等价。

`gpu-policy.json` 保存最多 512 条记录，达到上限淘汰最旧记录。文件绑定策略版本、引擎、GPU 包清单哈希、GPU 名称、驱动版本和主机 CPU 标识。绑定变化或文件无效时从空状态学习，不把旧引擎/别的硬件的结果当成本机事实。探测通过的结论 24 小时过期；负面记录 30 分钟起，每次重复失败加长，最多 6 小时。具体请求的失败哈希也有 30 分钟有效期。

同一时刻只有一个 probe，每 15 秒最多发起一个，超时上限 8 秒；超时后按既有恢复机制重建 worker，慢上下文留给 CPU。准备、计算、合并显示为“探测准备／探测计算／探测合并”。完整 GPU 行仍受 30 秒上限，探测和完整计算的错误证据保留原有诊断文件。

已学会且足够组成完整批量的场景优先于新探测。未知场景的 probe 超时只暂缓该场景，15 秒后重建 worker，不累加全局故障退避；驱动、进程、完整计算和重建故障仍按 15/60/300/600 秒退避。这样连续遇到慢场景不会让其他可用场景一起被罚等 10 分钟。

这使新武器无需客户端维护放行名单，但上游引擎升级仍需要匹配的原生和 GPU 二进制，不能拿旧 cubin 计算新引擎任务。当前自动测速要求本地同版 simfleet 原生 v3 库。

## 已执行验证

通用 worker 探测覆盖 Acceltra / demolisher / base、Kuva Hind / standard_multi_target / semi_auto、Larkspur Prime / standard_single_target / base 和 Zenith / demolisher / base。每组八个原始索引的完整 GPU 分片与 WASM 一致，随后每组四条正常 1000 次任务的完整评分与同版 CPU 一致。Kuva Hind 自动观察到更高私有页需求，完整批量使用更大的单局预算通过。

单元测试覆盖未来武器/榜单 ID、未来上下文字段隔离、构筑变化复用、负面记录过期、缓存绑定失效、探测原始索引、禁止探测带成绩、批次预算和结果 ID 匹配。实际 Fleet 冷/热缓存回放结果记录在 `experiments/gpu-board/adaptive-results.json`。

固定 Kuva Hind 多目标输入、4 条 CPU 线程、96 条正常任务的实际 Fleet 对照如下；该计时包含 GPU 冷启动，启动前的引擎校验不在 `REPLAY` 计时内：

| 模式 | 完整正确评分 | GPU 完成行数 | REPLAY 时间 |
|---|---:|---:|---:|
| 仅 CPU | 96 | 0 | 33.321 s |
| 空策略缓存、自动探测 | 96 | 40 | 21.729 s |
| 重启并复用缓存 | 96 | 46 | 20.095 s |

热缓存回放没有重复探测消息。三轮都与同引擎 CPU 参考逐项比较 score、metric、work；直接 worker 验证还比较完整评分含 counts。整个回放测试进程组峰值提交 6,719,926,272 字节，约 6.26 GiB。固定输入单轮对照不代表全站任务增幅。

已知慢的 Torid 多目标用例验证了负面路径：8 秒 probe 超时后记录为暂缓 30 分钟，GPU 重建就绪，原来的八条完整任务由 CPU 计算并逐项验证正确，probe 未提交任何结果。该回放进程族峰值提交约 3.18 GiB。

49 项 release 单元测试通过，7 项原有环境测试忽略。追加测试确认连续 20 次未知场景探测超时仍为 15 秒恢复，既不累加也不清除真正的运行故障退避。首次线上试跑也已经自动完成 10 条正常 GPU 任务；其间发现探测超时会误累加全局退避，最终版本因此增加了上述故障分类和已学会批量优先规则。

最终部署构建再次验证：慢 Torid 的八条回放任务全部正确，日志明确记录 15 秒恢复及重新就绪。线上已自动完成至少 19 条 GPU 任务，随后连续两次探测超时都按 15 秒重建；第二次恢复后采样到程序 GPU 使用率 96%。截至该次采样，部署进程组峰值提交约 5.76 GiB。这是部署验收记录，不代表已经完成多日稳定性测试。

追加 Furis / demolisher 对照：cycle 的八局 probe 约 4.26 秒，随后四条完整 1000 次任务共约 6.56 秒，完整评分全部与 CPU 一致；base 的同规模 probe 约 9.06 秒，在实际 supervisor 中会超过 8 秒限制，留给 CPU。同一武器的不同模式确实需要分别学习，不能把任一模式的结论套到整个武器。

最终策略的 Furis cycle 实际 Fleet 冷缓存回放：32 条任务中 15 条由 GPU 完成，全部 32 条评分与 CPU 参考一致，总耗时 24.306 秒（含初始化和探测）；该轮进程族峰值约 6.16 GiB。这证明无需手工放行即可在客户端从探测进入完整任务，不以此单轮数据宣称整个线上队列的固定增幅。

所有固定结果只对应记录中的引擎和硬件。没有把小样本 kernel 时间乘一个常数当成实际全队列速度，也没有取消状态、连锁或附加伤害以换取通过率。
