# GPU 榜单覆盖和资源显示

当前 `preview.6` 已替换本页的手工放行列表，使用[自动探测与学习](gpu-adaptive-dispatch.md)。下文保留固定场景的测量与限制，作为历史基准，不是当前客户端的武器白名单。

GPU 后端执行原引擎的完整战斗。能否计算正确，与是否适合交给 GPU，是两个不同的验证条件。首版只放行 Fulmin 是性能筛选范围有限；`0.9.0-preview.2` 增加以下两个场景，复用 `62a82930d1d3-sfg1-sm120` 模块。

| 自动分流场景 | 固定总工作量 CPU | CPU＋GPU | 吞吐比 |
|---|---:|---:|---:|
| Zenith / demolisher / base | 25.657 s | 20.391 s | 1.258× |
| Torid / demolisher / cycle | 62.281 s | 47.613 s | 1.308× |

条件：Ryzen 7 9700X，16 条 CPU 线程，RTX 5080，原生 AVX2 引擎和 GPU 引擎均为 `62a82930d1d3`。每条正常任务 1,000 次模拟，GPU 每批 16 条；CPU 计算 240 条、GPU 计算 64 条，对照 CPU 单独计算相同的 304 条。每个设备都生成完整评分，GPU 每个场景的 16,000 个完整分片逐局核对。基准先预热，然后先测 CPU 基线、再测混合，不能视为多轮实网平均。

现有 Fulmin Prime / heavy_gunner / semi_auto 继续分流。其他武器或同武器的其他场景不因名字相近自动放行。一个场景中不同构筑仍可能有不同耗时，故障和 30 秒超时会退回 CPU。

## Torid 为何在多目标上慢

Torid 爆破使的正常大批量已证实有额外吞吐，多目标则表现很差。相同 GPU 编译模块能生成与 CPU 一致的完整结果，因此不是“不支持 Torid 的附加伤害”。

为避免长时间占住显卡，诊断使用一局完整 180 秒战斗、原请求的第 0 个随机流，线程块 8、私有页预算 1 MiB；下面是单局诊断，不能与 16,000 局吞吐基准横比：

| Torid 多目标诊断 | GPU 时间 | 命中次数 | 触发次数 | 写入私有页 |
|---|---:|---:|---:|---:|
| 原始 cycle 请求 | 12.928 s | 86,331 | 91,313 | 58 |
| 同请求去掉赋能 | 12.416 s | 84,710 | 87,264 | 119 |

去掉赋能只是离线因果诊断，改变了战斗规则和结果，不能拿这个请求提交榜单。它没有显著解除 GPU 耗时，不能把瓶颈简单归到赋能。Torid 的 base 多目标用例也慢：16 局 GPU 约 28.94 秒，包含 978,503 次命中、484,772 次区域 tick 和 595,787 次触发。

从源码和计数可以确认，多目标涉及更多独立敌人状态、持续区域、连锁命中和事件更新。目前 GPU 实现是一条线程负责一局，通过转换后的 WASM 内存模型访问状态；这些随机访问、私有页写入和不同模拟之间的执行分歧可能放大开销。尚未用内核硬件 profiler 分离各项占比，不能宣称已经测出某一种开销占了多少。

继续加速需要优化事件/状态表示和内存访问，或为重负载建立更合适的设备代码布局，不能靠取消游戏规则换性能。简单把一局内的命中分给任意线程会牵涉事件顺序、随机流和浮点合并顺序，需要额外的等价性证明。

## 其他筛选结果

先用 16 局完整时长作筛选，包含普通步枪、光束、霰弹、范围伤害、投掷和转化循环，再将候选扩大到正常任务。小样本只能筛掉明显慢的路径，不能估计满批吞吐。

- Braton、Burston、Phenmor 的测试能给出正确结果，但当前通用 GPU 路径延迟高，未直接放行。
- Amprex、Ocucor、Tenet Arca Plasmor、Kuva Bramma、Xoris、Lex Prime 的小样本也有正确性证据；部分较慢，部分需要超过线上预算的私有页，尚未通过正常批量的收益验证。
- Kuva Hind 小样本通过，正常 16 行合批触发 `120` 私有页预算保护，保留 CPU。
- Kuva Nukor、Phantasma Prime 的完整战斗在加大到每局 1 MiB 私有页后仍触发 `120`，不是静默丢结果，保留 CPU。
- Larkspur 小样本与一次正常 GPU 合批通过；CPU 混合基准进程异常结束，当前没有完整可复核的吞吐结果，暂不放行。
- Boar、Laetum 和 Torid 多目标的部分 16 局筛选超时，已结束测试进程，不进入自动调度。
- Torid 的独立 `incarnon` 模式被引擎的榜单 order 接口拒绝；空赋能席位也被该接口拒绝。这两个不是 GPU 内核失败，去赋能的因果测试使用了明确标记的离线请求。

原始筛选、混合实验和失败状态保存在 `experiments/gpu-board/coverage-results.json`；复现脚本为 `survey.py`、`coverage_batches.py`、`tools/check-gpu-worker.py`。重型实验延续内存限额，主客户端仍以同一个 GPU 子进程处理有限批量。

## GPU 指示和占用的含义

客户端以明确的 IPC 阶段显示准备、计算、合并，待机时显示累计完成行数。当前批次不导出逐局完成计数，所以用转动指示和经过时间，不能把估算进度冒充实际百分比。

右侧“程序GPU”通过 Windows PDH 的 `GPU Engine(*)/Utilization Percentage` 采样，只匹配当前 GPU 子进程的完整 PID；读取所有引擎后取最忙引擎，避免把重叠引擎简单相加。独立和共享显存来自该 PID 的 `GPU Process Memory` 计数。采样在独立线程每秒进行，UI 和派单不等待计数器。启动首样本、失效或过期读数显示 `--`。

这与 Windows 任务管理器所描述的最忙引擎口径一致，表示 GPU 引擎忙碌时间，不是 CUDA SM occupancy，也不说明计算方法已经高效。[Microsoft GPU 计数说明](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)、[PDH 数组接口](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhgetformattedcounterarrayw)。实际 worker 负载中测到了约 78%–94% 占用，以及约 5.9 GiB 独立显存；其他应用的 GPU 使用不会记到这里。

## 部署验证

最终客户端 `0.9.0-preview.2` SHA-256 为 `c0fdbaebf1557b17f5e6a74b86d351ada042766dcbeb8b35a428085d5f09cf78`。41 项 release 单元测试通过，7 项原有环境测试忽略。UI 检查包含宽窗口、普通窗口和窄窗口，确认有状态、真实占用、无读数时的 `--`，以及不以 0% 表示不可观测的 GPU 逐局进度。

最终可执行文件的 worker 验证：Zenith 和 Torid 爆破使各 16 个不同种子、104 条完整评分均与原生一致，阶段顺序为准备、计算、合并；同时验证 PID 占用和显存计数、重复任务拒绝、引擎错配拒绝和设备互斥。该进程族峰值提交约 6.62 GiB。

从实际部署目录回放 96 条任务，16 条由 GPU 完成，全部评分一致；再次回放时主动结束 GPU 子进程，观察到回退，96 条评分全部正确。两轮进程族提交峰值约 6.86 GiB。部署保留原配置，并恢复正常运行。真实窗口采样时队列等待任务，右侧显示 GPU 待机、程序 GPU 0%、独立显存 2.07 GiB、共享 74 MiB，与独立系统计数一致。

这些验证证明功能、短程连续批次和故障恢复，不替代数天实网运行；新增场景的收益仍取决于实际队列和构筑。
