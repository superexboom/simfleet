# GPU 热点定位与精确 gas 存取

本轮固定引擎 `5c64c380e5f2`，基于现有 sfg2、96 寄存器上限和 32 线程 block，先定位开销再选择优化。生产实例只在设备测量时暂停，构建期间正常工作；构建与运行各自受 8 GiB 预算保护。

## 定位方法与边界

当前 Windows 驱动不允许此进程读取 NVIDIA 硬件性能计数器。作为替代，临时分析模块在大函数入口和返回处记录 `clock64`，只记录第一个 block 的第一个线程。每个样本运行完整 1000 次模拟，仍核对分片与最终评分。分析模块与生产模块隔离，计时指令不进入交付内核。

读数是该采样线程的包含子调用的时间，也包含 SIMT 分支等待。父子函数比例不能相加，不是所有 SM 的完整硬件采样，更不能单凭此结果判断 FP64 管线或缓存命中率。

| 函数 | Burston 采样占比 | Furis 采样占比 |
|---|---:|---:|
| `land_the_shot` 命中处理 | 80.07% | 79.71% |
| `process_ticks` 持续伤害处理 | 10.12% | 6.04% |
| `settle_procs` 异常状态结算 | 7.56% | 16.40% |
| `dlmalloc::malloc` | 0.32% | 0.21% |

因此本轮优先检查命中处理里的计算与存取，不重写低占比的内存分配路径。函数名由同版 bridge.wasm 的 name section 映射，最大的两个函数分别是 `land_the_shot` 和 `run_once_traced`。

## 已确认的生成代码开销

旧生成器对缓存 gas 的 64 位值使用 `memcpy`。在实际 PTX 中，这被展开为 8 条字节读取及一串移位、或运算；写入同样拆成字节。以命中处理为例，在结构体偏移 104～111 的连续字节读取后重新拼成一个 64 位值。这个计数器已对齐，拆字节没有语义上的必要。

候选生成器直接访问对齐的 `u64 cached_gas`。整数保持原位值，双精度类型用 CUDA 的位模式转换，不作数值转换；模拟规则、随机数、gas 计数、浮点精度、运行数量和评分均保持原契约。非缓存地址以及部分/非对齐访问仍走原有内存路径。

这一变更是否交付，以完整任务耗时和精确结果核对为准，不能把指令数量减少直接当作已测吞吐收益。

实际生成的 PTX 从 82,261,307 字节降至 67,935,724 字节，减少 17.4%。两个主要热点所在单元的局部字节读写消失，改为 64 位访问。此处记录的是静态生成代码，不是硬件动态指令计数。

此外对同一份 PTX 使用 CUDA 12.9 与 13.4.92 链接器进行单因素比较，精确除法、平方根、非 FTZ、禁用浮点乘加合并以及 96 寄存器上限均保持一致。链接器版本由工具读取 DLL 并记入构建记录，避免无意混用工具链。

## 计时与系统重启

原始 sfg2 的 Burston＋Furis 固定 4000 次模拟耗时 12.722 秒；gas 整字存取候选为 12.166 秒，局部吞吐约高 4.6%，全部分片及评分一致。CUDA 13.4 链接的同一份 PTX 为 12.033 秒，较 12.9 只差约 1.1%，单次短对照不足以证明更换工具链有稳定收益。

过程中机器意外关机，重启后 CPU 任务耗时普遍下降约 8%～12%，因此重启前后的整机时间不直接比较。补充同为 preview.13、空学习缓存、12 线程、8192 MiB 的配对对照：旧 sfg2 为 63.211 秒，gas 候选为 62.938 秒；都完成相同的 180 行，work 为 `1477082727900`。整机差异约 0.4%，不足以宣称明显提升。GPU 本轮分别完成相同的 39 行，但承接场景不同，不能把 GPU 分账增长直接当作内核加速倍率。

生产实例在这次异常关机后读回了 284 项学习记录；当时未部署候选内核。系统事件只确认意外关机，未据此推断具体硬件或软件原因。

## GPU 桥接层单独拆分弹丸结算

上游在 `fight/pellet.rs` 对 `settle_pellet` 使用 `#[inline(always)]`，注释记录了这个选择对 CPU 的实测收益。本轮只在隔离的 GPU 构建副本中改为 `#[inline(never)]`，观察能否减少 CUDA 巨型函数带来的开销；CPU DLL 和上游工作目录均不修改。gas 宏按函数体计权，不因内联属性改变计数；仍以完整分片与最终评分对照验证这一契约。

拆分后命中函数所在 PTX 单元从约 7.08 MB 降为 1.27 MB，独立弹丸结算约 5.04 MB。CUDA 12.9 链接由 719 秒降至 533 秒，但固定 4000 次模拟耗时 12.016 秒，比 gas 整字候选只快约 1.3%；全部分片、评分、gas 一致。运行收益不足以支持替换桥接层，因此该属性改动不进入默认构建。

## 复用研究工具

`experiments/gpu-board/profile_ptx.py <split-ptx-dir> <new-output-dir>` 在新的独立目录中添加软件计时。按通常方式链接，然后读取设备全局 `sf_profile`：每个函数占两个 `u64`，分别为调用数、包含子调用的时钟周期；顺序在 `functions.json`。每次测量后清零。只采样 block 0/thread 0，分析模块禁止混入发布套件。

`build.py --word-gas`（或直接 `retarget.py --word-gas`）启用整字 gas 实验路径；默认仍使用已部署实现。此开关重新生成的 CUDA 文件与已验证候选 SHA-256 一致：`7d4c8da5351810c9acac78efe234581f778b29abc12acdcc05009421ff9a4167`。`link_ptx.py` 读取 DLL 的实际版本并选择对应 API，构建记录包含版本，不再硬编码只接受 12.9。

## 可直接消除的调度损耗

完整回放还观察到：任务已经少于 CPU 收尾保留量、无法再给 GPU 分配整批时，客户端仍探测新场景。有一轮 Furis base 的探测耗费约 10 秒，却在这包结束前没有产生可提交的 GPU 行。

局部 preview.14 候选把是否探索新场景与同一个 CPU 收尾阈值绑定。没有可交给 GPU 的剩余份额时暂缓探测，下一批任务充足时继续学习。该候选完整通过 180 行评分核对，也确实消除了尾部探测，但本轮时间为 66.187 秒，没有证明整机吞吐改善。因此代码已撤回，变更补丁和实测记录保留在实验目录，生产继续运行 preview.13 与原 sfg2。

## 后续更值得验证的结构性限制

本机 84 个 SM，每个最多 1536 个线程，即 48 个 warp。现有一次仅启动 4000～16000 个线程，实际常见 12000 个；32 线程 block 下，全卡一共只有约 125～500 个 warp，平均每个 SM 约 1.5～6 个，即便全部同时驻留也远未达到线程上限。这个算术上限不能直接预测加速比例，但说明 100% 忙碌与足够多可调度 warp 是两回事。

继续加大批次受到每局私有 WASM 状态和页映射的约束：当前按 4 KiB 页复制，常见单局配额 192/256 KiB，另有映射和输出空间。8 GiB 合计提交上限下，简单提高 `MAX_RUNS` 容易重现内存故障。下一条更有价值的路线是减少每局实际私有状态及映射开销，再利用省下的预算扩大并行规模；例如验证更细的写时复制页和压缩页索引。它需要修改内核与 worker 的内存布局契约，应独立实施和测量，不能只改上限。

精简机器可读记录见 `experiments/gpu-board/hot-path-results.json`。本轮没有发布或部署任何候选套件，正式实例已恢复计算。
