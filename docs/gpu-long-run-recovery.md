# GPU 长时间运行后的停用与总内存预算

`preview.4` 运行约 1 小时 50 分钟时，现场状态是 GPU 故障回退 CPU、完成 449 行／资源回退 1 行，GPU 占用和显存为 `--`。进程列表只有主进程与守护，没有 GPU worker，确认为 GPU 已停用，而不是单纯没遇到合适任务。

当时 3,000 条 UI 日志已经轮换，保留的最早消息晚于故障发生；只读检查进程私有页也未找回具体错误。因此不能把这次故障断言为又一个 `120`、OOM、超时或恢复额度耗尽。

代码中确认了两项缺陷：临时故障的两次自动恢复按整个运行周期累计，成功计算不会重置；GPU 最后错误只写滚动 UI 日志，停用后长时间无法定位。`preview.5` 修复这两项，并在用户指定的合计内存预算内调整复杂任务容量。

## 恢复与可观测性

临时异常按 15、60、300、600 秒退避，之后维持十分钟最少间隔；成功处理至少八批、且从首次健康批次起超过一分钟才重置故障计数。偶发的一次成功不会造成不断快速重启。失败请求仍以有界哈希排除，不让同一批坏任务在每次重启后立即重试。

版本、架构、哈希、未知设备状态、输出协议和计算结果不一致属于需检查的错误，继续保留停用行为。恢复不能跳过正确性校验。子进程输出 EOF、网络管道断开、驱动错误、超时和无法获取 GPU 独占锁可退避恢复。

每次失败同时写入 `dispatch.log` 和 `gpu-diagnostics/last-failure.json`，前一份移为 `previous-failure.json`，最多两份；保留阶段、版本、引擎、错误、已完成数量和当前计算请求。没有账号、cookie、计算者身份和服务器租约。每份最多 8 MiB，写入临时文件后替换。原始计算请求使离线重放成为可能，但文件不应作为共享的凭据或配置文件。

UI 独立显示“待机：无合适任务”“待机：CPU收尾”“合适任务不足”“内存紧张”“恢复等待 Ns”“错误停用，需检查”。上次错误保留在资源栏，完整文本和请求保存在上述诊断文件。

## 8 GiB 合计预算

`compute_memory_limit_mb` 默认 8192，设置菜单的“CPU+GPU上限 MiB”可配置 4096～65536。Windows Job 限制 CPU 计算进程和它创建的所有 GPU 子进程的合计提交量。实际 Job 限制设为配置值减 64 MiB，为独立守护进程保留空间。改变上限使用现有排空／保存／自动重启流程，避免在正在运行的高占用进程上突然收紧限制。

该值是本程序计算进程的提交内存预算，不是系统全部进程占用，也不是显卡独立显存。资源区分别显示合计内存上限、系统内存、程序工作集和显存，避免混用统计口径。GPU 子进程自身还有 8 GiB 上限；如果全体配置更大，也不会让单个 GPU worker 无界增长。主进程原有 2 GiB 软回收线继续使用。

单局私有页可从 192 KiB 增到 384、768、1536 KiB，同时最多运行 16000、8000、4000、2000 局。因此扩大单局空间不扩大约 3 GiB 的私有页总缓冲。超限仍只回退整行 CPU，不使用任何部分评分。

派单前还会根据配置总预算和当前 CPU 主进程提交量缩减批量，预留驱动、快照和主机缓冲空间；预算放不下一条完整行时直接留给 CPU，显示“合计内存预算不足”。例如 4 GiB 设置、较低 CPU 占用、每局 192 KiB 时最多派约 2,000 次，不能继续沿用 16,000 次的大批量。硬 Job 限制仍是最终保护，分配估算不能替代它。

`tools/inspect-compute-memory.py <计算进程 PID>` 只读打开该进程的 Windows Job，读取真正的上限、峰值、成员 PID 和提交量，验证 CPU 与 GPU 是否属于同一限额。

## 验证记录

同一 GPU worker 的混批测试再现了一行 `120`，成功行和后续任务评分与 CPU 一致；提高单局预算后恢复，该 worker 随后完成 4,000 次常规模拟以及 1.5 MiB 预算下的 2,000 次模拟。实验进程族提交峰值约 6.19 GiB。

固定引擎的 Fleet 回放主动终止 GPU worker，15 秒后重建并再次就绪，96 行评分全部正确；故障文件保留 `exit code: 93`、计算阶段及本批请求。Windows Job 查询确认主进程和重建后的 GPU 同属合计限制：实际 Job 上限 8,522,825,728 字节（8128 MiB），为外部守护预留 64 MiB；该 Job 峰值约 6.54 GiB。包含测试驱动的外部测试进程族峰值约 6.69 GiB。

验证期间上游由 `62a82930d1d3` 更新为 `4296a0964da6`。原回放命令自动使用新引擎，因缺少对应 GPU 包而跑了 CPU，未将其记为 GPU 恢复通过。新增 `replay --release <json>` 固定版本后重新完成上述测试。线上客户端继续遵守原来的 48 小时原生等待策略及服务器接受期限。

最后一轮部署检查确认配置仅增加 `compute_memory_limit_mb=8192`，10 核预算和 3 路并发上限保留。运行中的 GPU worker 已重新出现、内存上限可从系统 API 读出；短程验证不能替代数小时到数天的稳定性验证。原先 449 行之后那次失败因证据已丢失，不能倒推出具体异常类型。
