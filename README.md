# simfleet

**WFSim 的志愿计算客户端**：把 [wfsim.app](https://wfsim.app) 网页里「帮 WFSim 计算」的那部分单独拿出来，做成一个命令行小程序。开着它，这台电脑就会按你给的预算，替 WFSim 计算排行榜分数和紫卡增益——跟开着网页一样，只是更快、更省、能常驻。

> 非官方项目，**基于 [WFSim](https://github.com/magenie33/wfsim)**（作者 magenie33，AGPL-3.0-or-later），与 WFSim 官方、Digital Extremes 均无关联。按 WFSim 的 [商标政策](https://github.com/magenie33/wfsim/blob/main/TRADEMARK.md)，衍生项目不能以 “WFSim” 命名，所以叫 simfleet。署名与许可详见 [NOTICE.md](NOTICE.md)。

（示意，实际是彩色的。）界面在终端的备用屏幕上原地刷新，退出后窗口恢复原样，并打印最后几十行日志。

- **左边**：每一路（一个计算 id）一个框，框里是它手头的任务、进度条、用了几个核，以及这一路自己的消息流；调度、引擎这类全局消息在下方「系统消息」里。只开一路时就是一个任务区加一整块日志。
- **右边**：本次得分和任务数、近 10 分钟的分/分钟、今日与累计、待确认；整机 CPU、本程序 CPU、内存和核心利用率的条；每个核心正在为哪一路计算（颜色对应左边的框）；全站在线人数和待算量；本周贡献榜（登录后标出你自己），积分旁是每个人**近半小时的每分钟得分**。网站的榜单不给计算时长，所以这个数是 simfleet 自己量的：每次刷新榜单时记下每人的累计积分，用半小时内最早的那次记录和现在相比，折算成每分钟；开始运行后第二次刷新（约 10 分钟）才有数，刚上榜的人要等下一次。
- **窗口窄于 96 列时**自动换成紧凑布局：一行贡献、一行 CPU/内存/利用率、任务列表和日志。
- **按键**：`P` 暂停/继续；`+`/`-` 调离开电脑时的核心数，按住 `Shift` 再按 `+`/`-` 调使用电脑时的核心数（减到 0 = 使用时暂停）——主键盘的 `+` 本身要按 Shift，所以调空闲核心数请用 `=`/`-` 或小键盘；`[`/`]` 调并发上限（最多同时开几路）；`L` 切换到全屏日志，`PgUp`/`PgDn` 翻看日志，`Q` 退出。按键改的核心数退出时会写回配置。
- **Windows 10 自带的控制台**（中文环境下 `·`、`●` 会画成两格宽）：启动时实测一次字符宽度并按实际宽度排版，每行都不写最后一列，并关闭自动换行，所以不会再出现一行溢出、整屏上滚成一排横线的问题。万一判断错了，可以设环境变量 `SIMFLEET_WIDE=1` 或 `0` 手动指定。

## 上手

0.8.1 优化了紫卡 lead 的重复元数据处理和中间报告。客户端会自动下载带 `-sfe1` 修订号的原生库，避免沿用同一引擎 ID 的旧构建。引擎在 [独立 Release](https://github.com/superexboom/simfleet/releases/tag/engine-872e90ffaf0d) 发布，客户端压缩包只包含程序、README 和许可说明。旧库保持可回退；技术细节见 [紫卡 lead 优化](https://github.com/superexboom/simfleet/blob/v0.8.1/docs/riven-lead-0.8.1.md)。

**下载**：在 [Releases](https://github.com/superexboom/simfleet/releases) 下载 `simfleet-<版本>-windows-x64.zip` 并解压。只需要 Windows 10/11 x64，不需要装 Rust 或任何运行库。

**Linux x64**：下载 `simfleet-<版本>-linux-x64.tar.gz`，`tar xzf` 后运行 `./simfleet/simfleet`（需要 glibc 2.35 及以上，如 Ubuntu 22.04+、Debian 12+）。Linux 上没有键鼠空闲检测，始终按「离开电脑时」的核心数计算；`priority = "idle"` 用的是 `SCHED_IDLE` 加 nice 19，只吃没人要的 CPU。放进 systemd 或 tmux 都行，收到 SIGTERM/SIGHUP 会先交还任务再退出；用 systemd 的 `Restart=` 管重启时可以加 `--no-watch`。

**macOS（Apple 芯片，M1 及以后）**：下载 `simfleet-<版本>-macos-arm64.tar.gz`，`tar xzf` 后在终端运行 `./simfleet/simfleet`（macOS 11 及以上）。simfleet 没有 Apple 开发者签名，第一次运行前在终端执行一次 `xattr -dr com.apple.quarantine simfleet`（或者先运行一次被拦下，再到「系统设置 → 隐私与安全性」里点「仍要打开」）。和 Windows 一样有键鼠空闲检测（离开电脑多久按 `idle_after_secs` 算）和电池检测（`pause_on_battery`）；计算时会阻止 Mac 因无人操作而自动睡眠（屏幕照常关闭），暂停或不计算时放开。原生引擎是 `engines/lib<引擎号>.dylib`，同样由 Action 编译发布、逐位比对后才用；WFSim 官方原生库从 2026-10-19 之后发布的第一个引擎起也有 macOS 版（`aarch64-macos`），自己的版本还没发布时一样先用它。

1. 把 `simfleet.exe` 放进一个文件夹（这个文件夹就是安装目录，配置和缓存都在里面；删掉文件夹就是卸载）。
2. 双击运行。第一次会问三件事：是否同意计算、离开电脑时用几个核心、要不要登录。
3. 之后每次双击就开始算。按 **P** 暂停/继续，**+ / -** 调整离开电脑时的核心数（加 **Shift** 调使用电脑时的），**Q**（或 Ctrl+C、直接关窗口）退出——退出前会把手头的任务交还服务器，不会让任务白白挂 30 分钟。

**意外退出会自动重启**：运行 simfleet 时其实是两个进程——一个只负责等待的守护进程，和它启动的真正干活的客户端。客户端崩溃（比如原生引擎里的访问违规）或程序内部出错时，守护进程把窗口恢复原样、说明原因，5 秒后重新启动它；启动后不到一分钟就又崩，等待时间依次加长，连续 5 次就不再重启。按 Q、关窗口、Ctrl+C、程序自己报错退出、任务管理器「结束任务」都算你自己要它停，不会被拉起。**多开互不影响**：每个守护进程只认它自己启动的那个客户端，同一个文件夹开几个窗口也只各管各的。每次崩溃在配置旁的 `simfleet-crash.log` 里记一条：错误码、崩在哪个模块的哪个位置、调用栈，反馈问题时发这个文件就行。不想要守护：`simfleet --no-watch`，或在 `simfleet.toml` 里写 `watch = false`。

不登录也能算：贡献先记在本机的计算者 id 上，**以后第一次登录时，之前攒的点数会一起转到账号名下**。

```
simfleet                 开始计算
simfleet --cores 8       本次空闲时用 8 个核心
simfleet --no-watch      不带守护运行（意外退出后不自动重启）
simfleet setup           重新设置预算
simfleet login           邮箱 + 密码登录
simfleet login --cookie <值>   用 Google/Discord/GitHub 登录的账号（见下）
simfleet logout          退出登录
simfleet status          查看本机和账号的贡献
simfleet bench           本机测速（不领任务）
simfleet bench --lanes 6 --repeat 5 --backend native   重复测速、核对结果并记录内存
simfleet bench --lanes 16 --repeat 5 --backend native --placement cache   对照缓存拓扑放置
simfleet cpu             看 CPU 识别结果：是否 Intel 大小核、计算线程会放在哪种核心上
```

**第三方登录的账号**（Google / Discord / GitHub）没有密码可输：在浏览器登录 wfsim.app → F12 开发者工具 → Application/存储 → Cookies → `https://wfsim.app` → 复制 `wfsim_session` 的值 → `simfleet login --cookie 那个值`。

## 预算与占用

| 设置（`simfleet.toml`） | 默认 | 含义 |
| --- | --- | --- |
| `idle_cores` | 核心数 × 30%（向上取整） | 离开电脑时用几个核心 |
| `active_cores` | 1 | 你在用电脑时用几个核心；`0` = 暂停 |
| `idle_after_secs` | 60 | 键盘鼠标多久没动算「离开」 |
| `pause_on_battery` | true | 用电池时暂停 |
| `priority` | `idle` | 进程优先级：`idle` 只吃没人要的 CPU，`below_normal`，`normal` |
| `core_type` | `auto` | 只对 **Intel 大小核**有效：`auto` 先 P 核、再 E 核、最后 P 核超线程，`p` 优先性能核，`e` 优先能效核，`windows` 交给系统（见下）；AMD 等其他 CPU 一律不生效 |
| `placement` | `auto` | 自动按 NUMA/末级缓存拓扑放置计算线程；`system` 交给系统，`numa` 优先节点内任务，`cache` 优先缓存域内任务 |
| `numa_nodes` | `[]` | 允许的 NUMA 节点列表，空表示全部；例如 `[0]` 将此进程放在节点 0 |
| `cpu_offset` | `0` | 按物理核心优先的处理器顺序轮转起点；多进程可设置不同起点，核心预算仍由 `idle_cores`/`active_cores` 决定 |
| `native_engine` | true | 有匹配的原生引擎时，榜单任务用原生（见下） |
| `slots` | 0（自动） | 同时开几路（几个计算者 id），见下文「调度」；填数字就固定开几路（仍不超过上限） |
| `max_slots` | 0（自动） | 最多同时开几路；0 = 逻辑处理器数的 1/4（2～16 路）。运行中按 `[`/`]` 调整，退出时写回 |
| `native_riven` | true | 原生引擎带紫卡搜索、并且启动校验与 wasm 一致时，紫卡增益也用原生（见「原生引擎」） |
| `official_engine` | true | 自己的原生版还没发布时，用 WFSim 官方的原生库算榜单（见「原生引擎」） |
| `watch` | true | 意外退出后自动重启（见「上手」） |
| `memory_limit_mb` | 2048 | 进程内存回收线，单位 MiB；持续超线一分钟后停止领新活，做完手头任务、保存结果，再自动换新进程；`0` 关闭 |
| `protocol` | 8 | 和服务器说话用的协议：8（一次同步交结果、续租、领活，见「调度」），或 7（旧的分开领、交、续租）。服务器要求时会在本次运行内自动改用 7 |

跟网页一样的规矩：没有你的同意不算；用电时算多少由你定；每份结果都要另一个**不同主人、不同网络**的电脑算出一模一样的数才算数，服务器还会抽查 5%。

## 调度：把预算里的核心用满

一个任务很难独自吃满一台机器。紫卡增益的快速下降法是「领头一步（单核）→ 本轮所有构筑分片打分（多核）→ 领头一步……」的链条，领头那几步只有一个核心在算；榜单任务能把 1000 次模拟摊到所有核心上，但结尾总有拖尾，任务之间还隔着一次网络往返。实测 16 核只跑一个任务时，**核心利用率只有 55%**。

simfleet 用的是分布式/批处理调度里的成熟做法：

- **榜单按包领取，一次同步办完所有事**（协议 8，WFSim [客户端约定](https://github.com/magenie33/wfsim/blob/main/docs/CLIENTS.md)「The cycle, protocol 8」）：每个计算者 id 只用一个接口 `/api/board/sync`。一次同步交上这个 id 存着的结果，列出它手上**所有**还没算完的行（这些行一并续租；**没列出的行服务器就收回**），报告引擎拒绝的行，顺便问之前交的结果确认了没有、这个 id 得了多少分，再按速度（`pace_ms`）要下一份活（`want_ms`，一包约这一路 10 分钟的活，最多 200 行）。回复里的 `next_ms` 是下次能领活的时间，提前去要服务器也不给。哪个核心空出来就从最早那包里开始下一行，上一行的拖尾和下一行的开头叠在一起。
  - **结果先存在本地**：每算完一行，结果马上写进配置旁边的 `kept/` 文件夹（每个 id 一个文件），等服务器回复说收下（`taken`）或作废（`dropped`）才删，所以回复丢了、程序崩溃或重启都不会丢结果，下次启动时补交。结果随下一次同步一起交：活快用完时（剩不到 2 分钟）、最早一条结果已经等了 10 分钟（`flush_ms`）、租约快到期要续租时，或者退出时。侧栏「待交」一行就是算完还没交的部分，「本次」是服务器已收下的；「速度」按算完的时候计。
  - **没活时看信号，不去问**：手上没活的 id 每 10 秒左右读一次 `cdn.wfsim.app/work.json`（这是 CDN 上的静态文件，不占服务器），上面说有活才在随机等几秒后去同步；信号的新旧按**服务器的时钟**判断（取自网站回复的 `Date`，本机时钟不准也不会误判）。信号读不到或过旧时退回每 2 分钟直接同步一次。闲着时每小时同步一次报个平安（`report_ms`）。
  - **参数听服务器的**：包多大、租约多长、多久交一次、多久看一次信号，都由服务器在每次回复和 `work.json` 里给出（`dials`），simfleet 只在第一次回复前用约定里的默认值。每个 id 的速度也存在 `kept/` 里，重启后第一次同步就能领到合适大小的包。
  - **退出时**每个 id 最后同步一次、什么都不列，手上的行全部交还，存着的结果一起交；连不上服务器时会重试约 45 秒，还交不上就留到下次启动。
  - 协议 7（`protocol = 7`，或服务器回 `fallback: 7` 时自动切换）：一包约这一路一分钟的活，答案每 30 秒和整包结束时交 `/api/board/answers`，每一行租约剩不到 2 分钟时单独续租（`/api/board/renew`）。紫卡增益两种协议都单个下发、单独续租和交答案。
- **手上同时最多两包**（`packs_held`）：当前这包剩下的活按这一路的速度不到 2 分钟（协议 7 是 15 秒）时就领下一包，核心不用等网络往返。紫卡增益只发给手上什么都没有的 id；协议 8 的同步列不出紫卡增益（它不是榜单行），同步一次就会把它收回，所以一个 id 在算紫卡增益、直到答案交上之前都不同步，这时由别的路接着领榜单。
- **多路（slots）**：一个浏览器就是一个 id，玩家本来就会多开浏览器来提高并发；simfleet 同样可以开几路，每路一个自己的 id，登录后都绑到你的账号（设备列表里显示为 `simfleet · 主机名 #2` 等）。服务器不让同一主人或同一网络的两个 id 互相确认，所以多开只增加算力，不增加「见证人」，不影响结果的可信度。
- **一个共享的核心池，紫卡优先，其余先来先算**（类似 Slurm 的 backfill / 工作窃取）：每个空闲核心先拿紫卡增益的活，再拿最早那个榜单任务的下一块，用不上的核心自动补给后面的任务，核心永远不等任务。紫卡优先是因为它的搜索是一条链（领头一步 → 这一轮所有构筑打分 → 领头一步……），哪一步被挤到后面，整个搜索都跟着慢；而榜单每块只占一个核心约 0.25 秒，让一让几乎没有代价。
- **紫卡增益的领头步骤固定在它自己的核心上**：搜索的状态存在那个 wasm 实例（原生时是那个计算线程）里，所以搜索结束前那个核心不接别的任务的活，原生的榜单块也不接：下一步领头只能在这个核心上算，排在一块榜单后面就得等它算完（实测紫卡因此慢 10–15%）。搜索一结束，这个核心的线程就换新的，搜索状态随旧线程释放（见下文「内存」）。
- **解析和合并也在计算核心上做**：一行榜单的每次模拟交回约 4 KB 的数据，要按顺序合并成结果。以前由调度线程解析、合并，6 核时就占了它一个核心的 1/6，核心再多它就跟不上，计算核心只能等它；现在解析和合并都作为任务交给计算核心，调度线程只拼接现成的文本（6 核实测从 17% 降到 1%），合并请求的内容逐字节不变。
- **网络从不阻塞计算**：同步、领任务、续租、交结果都在后台线程；协议 7「不带 ahead 的领任务」会让服务器收回这个 id 手上的任务，所以只有在这个 id 手上和路上都没有任务时才发。
- **一个 id 只给一个进程用**：协议 8 每次同步都会收回没列出的行，两个进程用同一个 id 就会互相收走对方的活。所以每个 id 在用时都在系统临时文件夹里加一把锁（按 id 的哈希命名，不含 id 本身）。同一份配置开了两次（同一个文件夹双击两次，或者把整个文件夹复制了一份），后开的那个会发现 id 被占用，自动改用配置里别的 id，不够就新建一个，日志里有一条「[多开]」说明。
- **国内线路**：和网站页面一样，同步、领活、交答案、续租、交还、查点数这几个请求（页面的 `RELAY_PATHS`，中转只放行这几个）每 10 分钟测一次直连和 WFSim 的香港中转（`cn.wfsim.app`）哪条快就走哪条；哪条丢了请求就立刻改走另一条，并一直用它到下次测速，两条都丢了就在下一次请求时重新测速。登录相关的请求只走直连，cookie 不经过中转。侧栏「线路」一行显示当前走的是哪条。交答案没收到回复会隔 3、10、30 秒重发（服务器对同一题只收一次，不会重复记分）。
- **开几路是测出来的，而且能开也能收**（多信号反馈控制）：每 20 秒看三样东西——核心利用率、手上积压的榜单够全部核心算几秒（按实测的每行成本折算）、最近有没有哪一路向服务器要不到活。
  - **加开一路**：利用率低于 95%、积压不到「领下一包的线」（协议 8 是 2 分钟，协议 7 是 1 分钟）、每一路都在干活、最近没有哪一路要不到活，而且离上次收回已过 1 分钟。
  - **收回一路**（最新的那路做完手头的活后不再接）：服务器暂时没有更多任务可分；积压超过一包加那条线的 1.5 倍（协议 8 约 18 分钟，协议 7 是 5 分钟）；或者核心已满（利用率 98% 以上）还积压一包加那条线以上（协议 8 约 12 分钟，协议 7 是 3 分钟）。
  - **为什么按包来定**：协议 8 一包是这一路约 10 分钟的活，剩 2 分钟时领下一包，所以不管开几路，所有路加起来手上的活大致在 2～12 分钟之间（路越多每路越慢，每包也就越小）；要开更多路，主要是因为算紫卡增益的那一路不领榜单，或者服务器给的包小。协议 7 一包只有约一分钟、最多 20 行，核心多的机器十几秒就算完，一路供不上，要多开几路。
  - **上限**：不超过 `max_slots`（默认逻辑处理器数的 1/4，2～16 路，运行中 `[`/`]` 调），也不超过当前预算核心数的一半。按键调低上限或预算变小时立刻生效。
  - **内存紧张时也收**：系统可用物理内存低于总量的 1/10（至少 1 GB）时，每 20 秒收回一路（固定了 `slots` 也一样），直到只剩一路；可用内存回到这条线的两倍以上并保持 1 分钟，限制才解除。每一路手上的活都占内存，一个紫卡搜索就要几百 MB（见下文「内存」）。
  - 面板标题栏显示「并发 当前/上限」，侧栏「并发」一行另外显示积压了几秒的活。

同一台机器（16 线程）、同样 16 核预算、各跑 10 分钟、都是紫卡增益调查任务：

| | 旧：一次一个任务 | 新：自适应多路并行（自动开到 2 路 = 4 个任务） |
| --- | --- | --- |
| 核心利用率 | 55% | **96%** |
| 完成的紫卡增益 | 7 个 | **12 个** |
| 提交的点数 | 约 1,133 | **约 1,951（+72%）** |

代价是单个任务变慢（大家分核心：单个紫卡增益从 44–163 秒变成 69–270 秒），换来总吞吐提高约七成。所有算法步骤与网页完全相同：新调度下的榜单和紫卡增益结果都和网页算法逐位一致（同样的构筑、分数、work、对战数）。

想固定路数（比如只想一路、保持单任务速度），在 `simfleet.toml` 里写 `slots = 1`。

## Intel 大小核

Intel 12 代以后的大小核 CPU 上，Windows 会把空闲优先级的后台程序（比如 simfleet）挤在 E 核上，而且不会往空着的 P 核上溢出。在 i5-13400F（6 个 P 核 12 线程 + 4 个 E 核）上实测：交给 Windows 时 8 条计算线程挤在 4 个 E 核上轮流跑，每条只拿到半个核心，P 核却闲着。所以 simfleet 自己排，按**档位**一档一档地填：

| `core_type` | 计算线程依次放在 | 适合 |
|---|---|---|
| `auto`（默认） | 每个 P 核的第一个线程 → E 核 → P 核的第二个线程（超线程） | 最快：一个 E 核比 P 核的超线程多出的算力更多 |
| `p` | P 核第一个线程 → P 核超线程 → E 核 | 尽量把活留在 P 核 |
| `e` | E 核 → P 核第一个线程 → P 核超线程 | 更省电、更不打扰前台 |
| `windows` | 不绑定，系统自己调度 | 想要原来的行为 |

13400F、预算 10 核、`auto` 时就是 6 条上 P 核、4 条上 E 核；预算 16 核时再加 6 条 P 核超线程。

做法是给第 k 条计算线程指定它所在那一档的 **CPU 集合**（Windows `SetThreadSelectedCpuSets`，Linux `sched_setaffinity`），集合里正好是这一档的逻辑处理器，所以一档里的线程不会比处理器多，系统也只会在这一档里挪动它。`auto` 和 `p` 同时告诉 Windows 不要按后台程序给它降频（关掉 EcoQoS），`e` 则打开。核心类别读的是系统报告的每个逻辑处理器的效率等级（Windows 的 EfficiencyClass，Linux 的 `/sys/devices/cpu_core`、`cpu_atom`），物理核按线程兄弟分组；只在 **CPU 厂商是 Intel、并且确实有两种以上等级**时才启用，AMD（包括带 Zen c 小核的型号）和其他 CPU 一律不动。

**不是计算线程的线程也管住**（0.7.0 起）：紫卡增益走原生时，WFSim 的优化器每一轮打分都另起一个工作线程来算，计算线程只在旁边等它（`optimizer/src/evaluate.rs`）。Windows 上新线程不继承创建它的线程的 CPU 集合，所以以前这些工作线程想跑哪就跑哪：P 核的超线程、预算还没轮到的 E 核都会被用上，任务管理器里看到的忙碌核心比 simfleet 排的多。现在整个进程的默认 CPU 集合就是预算内各档的逻辑处理器（`SetProcessDefaultCpuSets`），这些线程也只在里面跑。Linux 上新线程本来就继承创建者的亲和性，不受影响。

**看它实际拿到了多少**：面板右侧「实得」一行显示整个进程实际得到几个核心（进程的 CPU 时间 ÷ 经过的时间）、每条在干活的计算线程平均拿到一个核心的百分之几，以及计算线程实际落在几个逻辑处理器上。以前只数计算线程自己的 CPU 时间，而原生紫卡增益的活其实是在上面说的工作线程里算的，计算线程那时在等，于是「实得」会比实际少很多；现在数的是整个进程。挤在少数核心上，或者被别的程序抢走了 CPU，都会直接显示成每线程远低于 100%，持续一分钟就在日志里提示一次。这一项对所有 CPU 都有效。

和任务管理器对照时注意：Windows 10/11 任务管理器的 CPU 百分比默认是「处理器效用」，按当前频率相对基础频率折算，睿频时一个忙着的核心可以算到接近两个核心的百分比。simfleet 的 CPU 条和「实得」按时间计（忙了多少时间），睿频高的 Intel CPU 上会比任务管理器低；资源监视器、Process Explorer 显示的是按时间计的数。「核心」一行里每格的 `P`/`E` 是那条线程最近实际跑在哪种核心上。识别结果和分配方案用 `simfleet cpu` 查看；首次设置时检测到 Intel 大小核也会问一次。

**Apple 芯片（macOS）**：macOS 不允许把线程绑到指定核心，只能给线程设 QoS 等级，由系统按等级挑核心：`background` 只在能效核上跑，更高的等级优先用性能核、满了再用能效核。所以在 Apple 芯片上 `core_type` 的意思是：`auto` 用 `utility`（性能核优先，能效核也用，让着你正在用的程序；`priority = "normal"` 时用 `user_initiated`），`p` 用 `user_initiated`，`e` 用 `background`（只用能效核，最省电、最安静，也最慢），`windows` 不设等级。紫卡增益走原生时优化器另起的工作线程继承计算线程的等级。M 系列没有超线程，上面 Intel 的超线程问题在这里不存在；系统不告诉程序线程跑在哪个核心上，所以面板不显示每格的 `P`/`E` 和处理器个数。`simfleet cpu` 显示芯片型号、性能核和能效核个数以及当前的等级。

## Go 还是 Rust：实测

关键事实：网站对客户端结果做**逐位比对**，所以客户端必须跑和浏览器完全相同的引擎；而 WFSim 发布非常频繁，引擎号（源码哈希）一变，旧引擎就领不到任务。所以最省心的做法是**直接下载网站正在发布的那个 wasm 引擎来跑**——客户端本体不用跟着更新。宿主语言本身几乎不干活，速度取决于 wasm 运行时的编译器。

同一条真实榜单（Braton Prime · demolisher · cycle · 1000 次模拟，单核）：

| 运行方式 | 用时 | 相对浏览器 | 结果 |
| --- | --- | --- | --- |
| 浏览器 V8（Node 24 里跑同一个 wasm） | 4.36 s | 1.00× | 与榜单一致 |
| **Go** + wazero 1.9（纯 Go wasm 运行时） | 8.95 s | 0.49× | 一致 |
| **Rust** + wasmtime 49（Cranelift） | 6.90 s | 0.63× | 一致 |
| **Rust** 原生编译 WFSim 引擎 | 3.83 s | 1.14× | 一致 |

多目标榜单（standard_multi_target）：V8 13.7 s，wasmtime 18.0 s，原生 11.5 s，三者都与榜单逐位一致。

结论是 **Rust**：
- wasm 路线上 wasmtime 比 wazero 快约 30%，且对 `externref` 支持完整（Go 的 wazero 目前连导出函数都要绕坑）；
- 更重要的是 WFSim 引擎本身就是 Rust，只有 Rust 能把它**原生编译**进来——比 wasm 快 2 倍、比浏览器还快；Go 只能通过 cgo 绕一圈；
- 本体 9.7 MB，单文件、无运行时依赖。

simfleet 因此有两个引擎：
- **wasm（默认，永远可用）**：运行网站当前发布的 `/pkg/wfsim_wasm_bg.<摘要>.wasm`，按文件名里的 sha256 校验，编译一次后缓存；网站发新版时自动下载新引擎，客户端不用更新。
- **数据包**（0.7.1 起）：WFSim 把引擎拆成了代码和游戏数据两部分（客户端约定「The official data pack」），`release.json` 的 `data` 指明这一版的数据包 `/pkg/pack.data.<摘要>.json`（约 4.6 MB）。simfleet 和 wasm 一起下载、按文件名里的 sha256 校验、存进 `cache\`，每个 wasm 实例第一次计算前装进去（`install_data_bytes`），WFSim 官方原生库（接口版本 2）加载时装一次。**2026-10-25 01:00 UTC 起网站的引擎不再自带数据，不装数据包就算不了任何东西**，所以 0.7.0 及更早的版本到那时就领不到能做的活了，要更新。simfleet 自己编的原生版是 WFSim 那次提交的普通构建，数据编在里面，不需要数据包。
- **原生（自动，更快）**：`engines/<引擎号>.dll`，由本仓库的 Action 从 GitHub 上与网站引擎号完全相同的那次 WFSim 提交编译并发布，simfleet 自动下载（见下文「原生引擎」）。每次启动都会在一条金丝雀榜单上和 wasm **逐步逐位比对**，不一致就自动停用。紫卡增益也能用原生（见下文「紫卡增益走原生」），同样要先过一次和网站 wasm 的比对。

本机（16 线程）实测，同一条榜单：

| | 1 核 | 16 核 |
| --- | --- | --- |
| wasm | 6.9 s（145 次/秒） | 0.95 s（1,057 次/秒） |
| 原生 | 3.8 s（261 次/秒） | 0.44 s（2,284 次/秒） |

紫卡增益（dual_toxocyst 一个真实调查任务）：网页算法在 V8 单线程 472 s；simfleet 16 核 117 s；**最终构筑、分数、work、对战数与网页算法完全相同**。

**内存**（0.6.8 起，16 核实测）：
- **榜单**：原生引擎只跑榜单时整个程序约 150–350 MB。
- **wasm**：每个核心一个实例，算过活后约 50 MB（和浏览器一个 worker 一样），实例的内存只增不减。一个计算线程改用原生后 30 秒不再碰 wasm，就把实例丢掉；以前要等这个核心整整空闲一分钟，可榜单不停的时候核心从来不空，实例就一直留着。
- **紫卡搜索**：一个紫卡增益的搜索状态（WFSim 优化器里所有打过分的构筑、候选列表、筛选留下的模拟数据）存在领头核心的线程里，一次搜索约 250 MB（构筑越多越大），wasm 里还更多。WFSim 只在**同一个线程**开始下一次搜索时才清掉它，而下一个紫卡增益的领头多半落在别的核心上，所以旧版每个当过领头的核心都留着一份：16 核下最多 16 份，再加上每个核心的 wasm 实例，几个小时就能吃到好几 GB。现在搜索一结束（算完或交还），领头核心的线程就退出、换一个新的，这份状态随线程一起释放。
- **空闲的核心**：一分钟没活的核心整个线程退出（预算变小、暂停、活不多时），连同 wasm 实例和分配器替它留着的内存；有活时再新建线程，开销可以忽略。
- 实测 4 个紫卡增益同时算：旧版算完后仍占 1.5 GB，以后越积越多；现在算完回到约 500 MB，一分钟后回到 150 MB 左右。同时算的时候还是要 1.5 GB 上下，这是 4 份搜索状态本身的大小，内存紧张时少开几路（上文「调度」）。

**长期运行的内存回收（0.7.4 起）**：`memory_limit_mb = 2048` 是回收触发线，单位 MiB。Windows 看进程的私有提交量，Linux 看驻留量加交换量，macOS 看驻留量。持续超过一分钟才开始回收，达到两倍时立即开始。回收时停止领新活，已有任务继续计算、续租和交结果；手头清空后自动换新进程。最多等 15 分钟，仍未完成的任务交还，已完成的结果保存在 `kept/` 中，下次启动补交。落盘失败会重试，保存成功前不会因内存维护退出。配置中的 id、登录信息和核心预算会保留。

这是**软触发线**，排空任务期间可以超过它。`0` 关闭。默认守护进程在旧进程退出后立即启动新进程，不算崩溃；`--no-watch` 下也会主动换进程，外部进程管理器需要保持 PID 时可设为 `0`。每次换进程，面板的「本次」计数重新开始，账号贡献和待交结果继续保留。

结束计算线程只能释放线程自己的搜索状态。原生引擎还有全局缓存、请求路径中永久保留的分配，以及 DLL 卸载后分配器没有归还的页面；WASM 的线性内存也不会缩小。换进程由系统收回整个地址空间，因此这些内存都能回收。上游引擎保持原样，客户端继续逐位验算。

`tools/check-maintenance.py` 可以在本机模拟协议 8，连续检查排空、交结果和自动换进程。它使用虚构 id 和本地服务器，不领取真实任务；需要 Python 和 `psutil`，参数见脚本帮助。初始内存调查见 [审查报告](https://github.com/superexboom/simfleet/blob/v0.8.1/docs/performance-2026-10-21.md)，0.8 的性能数据与 NUMA 配置见 [吞吐报告](https://github.com/superexboom/simfleet/blob/v0.8.1/docs/throughput-0.8.md)。

## 原生引擎（自动）

**0.8 原生快速路径**：新版 DLL 有 `sfe_board_abi=1` 时，一行榜单在计算线程准备一次不可变战斗参数，局与局之间复用；每局仍调用原来的模拟函数，保留原来的 seed、index 和顺序合并。分片与累加器留在 DLL 内，客户端只接收进度和最后分数。普通浮点值直接保留其位模式，超出 JS 整数精度范围、负零或非有限值通过原规范化逻辑处理。启动时先以 1 局、7 局和逆序切片对照 WASM，一致才启用。旧 DLL 或官方库没有这个入口时继续走普通接口；环境变量 `SIMFLEET_NATIVE_FAST=0` 可临时关闭，便于同条件对比。紫卡评分同时复用线程上最近一个冻结请求的解析计划，请求形状改变或开始新搜索时替换，线程结束时释放；缓存不保存完整搜索结果。

**多插槽 Xeon、AMD 多 CCD/X3D**：`simfleet cpu` 显示 NUMA 节点、处理器组、末级缓存容量和计算线程顺序。`placement=auto` 在多节点、多缓存域或 Intel 大小核上启用拓扑放置，单节点单缓存的普通 CPU 保持系统调度。先分配物理核心，再用 SMT；同一 NUMA 节点内优先较大缓存的 CCD，但不会为了大缓存提前使用 SMT、放着另一 CCD 的物理核心不用。多个节点按物理核心轮流分配预算，每个任务优先留在起始节点/缓存域，空闲线程可跨域接活。计算线程绑定完成后才初始化战斗参数，尽量让内存首次分配发生在使用它的节点。Windows 支持超过 64 逻辑处理器的处理器组，Linux 尊重进程允许的 CPU 集；macOS 继续使用现有 QoS 机制。

同机多开 10 线程进程时，可分别设置 `cpu_offset=0/10/20`；若要按插槽分开，先用 `simfleet cpu` 查实际节点，再设置各自的 `numa_nodes=[0]`、`[1]`。这是固定划分，不会自动感知其他进程的预算；配置要避免重叠。`placement=system` 与节点/偏移选择不能同时使用。X3D 和多插槽 Xeon 的实际收益要在对应机器上测量，单 CCD 9700X 的测试不能替代。

复测示例：`simfleet bench --lanes 16 --repeat 5 --backend native --placement cache`；`--placement system` 对照系统调度；`--order order.json` 指定固定榜单输入。计算多个已保存任务可用 `simfleet replay task1.json task2.json --lanes 16 --placement numa`，结束会打印总时间，不提交结果。

不用自己编译，也不用自己选。对网站正在用的引擎号，simfleet 依次找：

1. **simfleet 自己发布的版本**（下面说的 Release `engine-<引擎号>`）：有 AVX2 版，紫卡增益也能走原生；
2. **WFSim 官方的原生库**：网站发布新引擎几分钟后就有（[客户端约定](https://github.com/magenie33/wfsim/blob/main/docs/CLIENTS.md)「The official engine library」）。simfleet 先用 WFSim 的公钥验证清单的 Ed25519 签名，再核对文件大小和 sha256，任何一项不符都不用。它只有网页接口（`api`），所以只算榜单，紫卡增益仍走 wasm；不想用就把 `official_engine` 设为 `false`；
3. 都没有就用 wasm。

不管用哪一个，都要先在金丝雀榜单上和**网站自己的 wasm** 逐位比对一致才用。用着官方库时，simfleet 每 10 分钟看一次自己的版本发布了没有，发布了就不停机换上。

**内存分配器**：原生引擎和 simfleet 本身都用 [mimalloc](https://github.com/microsoft/mimalloc)，每个线程有自己的堆。原来用的是 Windows 的进程堆，所有线程共用一把锁。曾经有一台跑了几个小时的客户端，10 条计算线程每条只拿到四成算力；暂停线程看调用栈，约一半时间都在 `RtlAllocateHeap` 里排队等这把锁。核心越多、跑得越久，排队越严重。WFSim 官方的原生库也用 mimalloc。分配器不改变任何一位结果，发布前照样逐位比对。

**所有原生库都在一条专用线程上加载**（0.6.7 起）：mimalloc 的 v3 内核（WFSim 官方库用的就是它，simfleet 0.6.6 之前编的版本也是）把「加载这个 dll 的线程」当作它的主线程。以前新引擎是在一个临时的后台线程里下载、加载的，这个线程一结束，主堆就跟着被拆掉；之后系统在同一块线程内存（TEB）上新建的线程一调用这个库就读到空指针，进程直接以 `0xC0000005` 消失。切换引擎（换上官方库、或者从官方库换到自己的版本）后过几分钟崩溃，就是这个原因：最小复现里只要新建约 250 个线程就必崩。现在加载和卸载都在一条和程序同生命周期的线程上做，它永远不结束，这个问题就不会再出现；官方库、旧的 v3 版本都实测通过（`cargo test --release lib_outlives_its_opener -- --ignored`）。simfleet 自己编的版本从 0.6.6 起用 mimalloc 的 v2 内核，本来就不受影响。

本仓库的 [native-engine](.github/workflows/native-engine.yml) Action 每 10 分钟计算一次 WFSim `main` 分支的引擎号（避开整点和半点：GitHub 负载高时会丢掉定时任务，整点最严重，原来的「每 30 分钟」曾连续 5 个小时一次都没跑；一次构建结束时 `main` 又换了引擎就马上再跑一次；同一个引擎编失败了，定时任务 3 小时内不再重试，手动触发随时重编）（wfsim.app 对 GitHub 的服务器会弹出人机验证，所以 Action 完全不访问网站；网站发布的引擎号就是它所用源码的哈希）。遇到还没发布过的引擎号，它会在那次提交上，用 WFSim 自己锁定的 Rust 和 wasm-bindgen 版本：

1. 照 WFSim 的做法编译出 wasm，作为比对的参照；
2. **把 Digital Extremes 的卡牌文本清空**（`tools/strip_card_text.py`），然后从对应提交编译原生引擎。0.8 起在本地应用 `native-engine/patches/` 中适配成功的补丁：批次预处理入口、单线程直接评分、固定元数据复用；战斗模拟和 gas 计数代码保持原样，补丁清单随构建保存。每个平台编两份：一份任何 x86-64 都能跑，一份是 x86-64-v3（即 AVX2、FMA、BMI2 这一代指令，2013 年以后的 CPU 基本都有）。Windows 是 `<引擎号>.dll` / `<引擎号>-v3.dll`，Linux 是 `lib<引擎号>.so` / `lib<引擎号>-v3.so`；macOS（Apple 芯片）只编一份 `lib<引擎号>.dylib`，这个目标的基线就是 M1 的指令集，所有 M 系列都能跑。WFSim 对卡牌文本没有授权（见其 [LICENSE-DATA.md](https://github.com/magenie33/wfsim/blob/main/LICENSE-DATA.md)），所以发布的版本里不含它；引擎只拿这些文本做显示，不影响任何分数；
3. 在 WFSim 仓库里提交的榜单快照上取一把武器（Braton Prime）的 8 条真实榜单（4 把尺子 × 2 种模式），每一份都和参照 wasm **逐位比对**（`simfleet check-native`：分数、work 和 gas），全部一致才发布。某个平台没通过就不发布它，那个平台继续用 wasm；
4. 发布为 Release `engine-<引擎号>`，附 sha256，说明里写明对应的 WFSim 提交、simfleet 提交和构建记录。已经发布的文件从不替换，只补缺的。

**本地发布更快**：Action 因为访问不了网站，每次都得先自己编一份参照 wasm，很慢。维护者在自己电脑上运行 `tools\publish-native-engine.ps1`：编两份 Windows 版，每份都直接和**网站正在用的 wasm** 比对 32 条榜单、WFSim 客户端约定里的 gas 测试向量（`tests/gas/rows.json`）和紫卡校验，全部通过才上传缺的文件。Linux 版仍由 Action 补上——它发现 Windows 版已经在了，就只编 Linux。

**紫卡增益走原生**：WFSim 的优化器本来就保证原生与 wasm 算出同一个结果——随机种子与线程数无关，紫卡搜索的状态是每个线程自己的（就像浏览器里每个 worker 一个实例）。唯一的差别是每批评估的候选数：wasm 固定 16 个，原生是「工作线程数 × 4，至少 16」，而原生默认用「核心数 − 2」个线程，所以 6 个线程以上的机器上原生的搜索路径会和浏览器不同。WFSim 的请求本身就有 `threads` 字段，原生入口（`sfe_optimize`）给每个请求写上 `threads: 1`，每批就正好 16 个；这个字段只会出现在结果行的回放请求里，不进紫卡增益的答案（构筑、分数、work）。本地优化不改变每批候选数、搜索路径或随机种子；单工作线程时直接在现有计算线程执行，不再另建线程等待。

每次启动，simfleet 在后台线程上用一个小的紫卡搜索把原生和网站的 wasm 各跑一遍（领头、两片打分，和真实任务的流程一样，十来秒），**结果完全相同才让紫卡增益走原生**；这十来秒里领到的紫卡增益先等它的结论再开始（一个紫卡任务从开始到结束只在一边算，中途不换。以前是直接用 wasm 开始，结果整个任务都在 wasm 上算完，每个参与打分的核心各建一个 wasm 实例，16 核一下就多出 800 MB）。不一致就只用于榜单，`native_riven = false` 可以关掉。实测一个真实的紫卡任务（dual_toxocyst，180 秒战斗、4 个起点，2 核）：wasm 417 s，原生 **240 s**（快 1.74 倍），最佳构筑、分数 274.4998410739098、work 205,792,130,138、41,084 场战斗、6,761 个构筑全部相同，和浏览器 V8 的参照结果也一致。

simfleet 只用网站**实际发布**的引擎号：启动时在 `engines\` 里找对应的 dll，没有就去 Release 下载，校验 sha256，再在金丝雀榜单上和**网站自己的 wasm** 比对一次，一致才用；运行中没有原生引擎时每 10 分钟再看一次有没有发布出来，有就在后台下载、比对，通过后不停机换上：已经在 wasm 上开始的紫卡增益照常在 wasm 上算完，之后的任务走原生，不用重启。不想用原生引擎，把 `simfleet.toml` 里的 `native_engine` 设为 `false`；只想用自己编译的，把 `native_engine_url` 设为 `""`、`official_engine` 设为 `false`。

**按 CPU 选版本**：CPU 支持 AVX2 那一代指令时用 `-v3` 版，否则用通用版；`-v3` 不可用或比对不一致时自动退回通用版。两份算出的结果逐位相同（Rust 不会擅自合并乘加、也不会调换求和顺序）。在 Ryzen 7 9700X 上实测 Braton 榜单（1000 次模拟）：

| 编译目标 | 1 核 | 2 核 |
|---|---|---|
| 通用 x86-64 | 4.99 s | 2.60 s |
| **x86-64-v3（AVX2）** | **4.47 s（快约 11%）** | **2.34 s** |
| x86-64-v4（AVX-512） | 4.56 s | 2.28 s |
| znver5（只针对这颗 CPU） | 4.46 s | 2.34 s |

AVX-512 没有额外收益：引擎是一场场按事件推进的战斗模拟，分支多、几乎没有能成批向量化的数值循环，提速来自更新的标量指令，AVX2 那一代就已经有了。同理也不适合 GPU：GPU 的超越函数与 CPU 不逐位一致，而 WFSim 要求两台不同机器的结果逐位相同才算数。想强制用某一版，设环境变量 `SIMFLEET_CPU=baseline` 或 `SIMFLEET_CPU=v3`。

自己编译（要 git、Rust、Python：引擎号由 `tools/engine_id.py` 按那次提交自己的 `build_site_app.py` 里的算法计算，WFSim 改了算法也跟着变）：

```
powershell -ExecutionPolicy Bypass -File tools\build-native-engine.ps1 [-Strip] [-Cpu x86-64-v3]
pwsh tools/build-native-engine.ps1 [-Strip] [-Cpu x86-64-v3]      # Linux
simfleet check-native [--rows tests/gas/rows.json] [--lanes N] [--weapons 1-4]   # 和网站的 wasm 逐位比对（默认 4 把武器、32 条）
simfleet check-native --engine <引擎号> --wasm <参照 wasm> --data <数据包> --boards <WFSim>/site/board   # 离线：参照 wasm 先装数据包再比对
powershell -ExecutionPolicy Bypass -File tools\publish-native-engine.ps1 [-Lanes N] [-Jobs N] [-NoUpload]   # 维护者：编译、检查、发布
```

**网站引擎更新时**：WFSim 的引擎随武器实测几乎天天变，旧引擎在被替换后 3 天内仍被接受（客户端约定里的 `accepted`）：只改了武器数据时，没改的武器照常算、照常计分；代码也改了时（`join`），答案只能给网站引擎的答案作证，不能单独成为结果。服务器给旧引擎派活时会附上网站现在的引擎号（`work.json` 信号里也有），simfleet 一看到就在后台准备新引擎（wasm，加上能找到的原生版）。准备好后不再接新活，手上的做完就换上新引擎接着算，不用重启，也不会交还任何任务；旧引擎算的结果随后单独用旧引擎号交上（这次同步不列任何行，换引擎时每一路手上都是空的）。宽限期过了服务器才会回 `stale`，那时手上的任务交还，直接换上已经准备好的新引擎。

## 怎么做到「和浏览器一模一样」

协议逐条照搬网页的 `69-board-work.js` / `08-checkpoint-api.js`（WFSim 源码）和 [客户端约定](https://github.com/magenie33/wfsim/blob/main/docs/CLIENTS.md)：

- 协议 8：`/api/board/sync` 一个接口（带同意书版本与时间、协议号 8、可用核心数、每行耗时 `pace_ms`、要多少活 `want_ms`、手上所有行 `held`、存着的结果 `results`、引擎拒绝的行 `refused`、要查的结果 `states`、查分的起点 `since`）；中断就同步一次什么都不列，紫卡用续租接口的 `release`。协议 7：`/api/board/work` 领任务，快做完时提前领下一份（`ahead`），榜单包用 `/api/board/answers` 的 `done` 交还；
- 榜单：每一行 `/api/board/order` 取对战（引擎不接受的行在下次同步里报告）→ 各核并行跑 `/api/board/runs`（每局一个 shard）→ **严格按局序** `/api/board/fold` → `/api/board/score`，答案连同 `counts`/`lanes`/`compute_ms` 存进 `kept/`，随下一次同步交（协议 7 攒进包里，每 30 秒和整包结束时交 `/api/board/answers`）；
- 公开的数（网站在算的电脑数、待算的榜单、排行榜）和网页一样先读 `cdn.wfsim.app` 上的文件，读不到才问服务器；登录后排行榜仍问服务器，因为只有它能标出你自己那一行；
- 紫卡增益：`quick_fleet` 下降，lead 永远在 0 号核的同一个实例上，评分切片每核两片，2 分钟续租一次，结果按 `boardPayloadFromResult` 组装后交 `/api/appraise/<code>/result`；
- 所有在引擎之间传递的 JSON 都按 `JSON.parse`/`JSON.stringify` 的语义处理（数字转 f64、`-0` 写成 `0`、整数键排前），保证喂给引擎的值与浏览器逐位相同。
